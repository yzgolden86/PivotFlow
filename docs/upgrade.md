# 升级与回退

升级 PivotFlow 时，要一起确定程序版本、数据库拓扑、凭证主密钥和持久目录。只替换镜像或二进制不能保证原数据仍可读，也不能保证以后能无损降级。

## 版本和产物

正式发布工作流接受两种标签：

| 标签 | GitHub Release | 容器别名 |
| --- | --- | --- |
| `vX.Y.Z` | 正式版本 | `latest` |
| `vX.Y.Z-beta.N` | 预发布版本 | `beta` |

程序内的 UpdateManager 只检查 `stable` 或 `preview` 渠道，不会替换当前程序；Docker 相关自动检查已禁用。它显示有更新不等于当前部署会自行升级。

容器别名只是入口。工作流成功写入 `latest` 或 `beta` 标签，也不能证明当前公共仓库的别名仍指向预期版本。升级目标应固定为完整版本标签并记录 manifest digest；条件允许时，在 Compose 或部署清单中直接固定 digest。源码树有未提交改动、镜像只有本地标签，或只在分支上看到构建产物，都不构成可部署的公开版本。

## 升级前核对

先记录当前版本、提交、构建时间和准确镜像 digest（或自有二进制的 SHA-256）。同时保存解析后的 Compose/服务配置、程序参数和启动用户。不要只写“之前是 latest”。

| 项目 | 事实 | 升级前动作 |
| --- | --- | --- |
| 存储 | 一个 MySQL DSN、一个 PostgreSQL DSN 或 SQLite，三选一 | 明确当前拓扑；同时设置 MySQL 和 PostgreSQL DSN 会直接致命退出 |
| SQLite 路径 | 未显式设置时可能因 `data` 不可写而回退到系统临时目录 | 生产必须显式设置持久 `SQLITE_PATH` |
| 混合副本 | 只有 `PIVOTFLOW_ENABLE_SQLITE_REPLICA=1` 才启用，其他值都视为关闭 | 从实际启动配置确认，不要猜测 |
| 副本恢复 | 主库权威；`PIVOTFLOW_SQLITE_LOG_DAYS=0` 不恢复日志和请求历史 | 记录日志恢复天数并接受历史窗口差异 |
| 容器数据 | 发布 Compose 绑定 `./data`，源码构建 Compose 使用命名卷 `pivotflow_data` | 确认即将升级的是哪一个卷或绑定目录 |
| 文件权限 | 官方镜像以 UID/GID `1001:1001` 运行 | 检查数据库、密钥和计费日志可写，不以 root 运行绕过 |

程序没有来源不同的多套主密钥。主密钥选择顺序固定为：

1. `FUSION_MASTER_KEY`；
2. `FUSION_MASTER_KEY_FILE`；
3. `SQLITE_PATH` 同目录的 `fusion-master.key`，未设置路径时为 `data/fusion-master.key`。

`FUSION_MASTER_KEY_VERSION` 默认是 `v1`，版本作为认证 AAD 的一部分参与校验。系统没有 keyring 自动找回；错误密钥会让密文无法解开并阻止启动。更换程序时必须带上匹配的密钥和版本，不能删除旧数据库旁的密钥后让程序重新生成。

升级前按[备份与恢复](backup-recovery.md)制作一致备份。至少包括主库、每个实例本地计费日志、主库结算回执、主密钥及版本、启动配置和旧程序产物。SQLite 不能只复制正在写入的主库，必须停服或使用 SQLite 快照；计费日志同样要与其主库时点配套。

## 先做隔离演练

在数据库副本、计费日志副本和隔离的远端数据库克隆上启动目标版本。阻断测试实例对真实上游、通知、WebDAV 和支付系统的访问，只允许测试资源。记录启动日志、迁移耗时、凭证解密结果、计费待处理数和历史窗口。

不要用“启动一次看看能否迁移”的方式直接碰生产数据。启动没有 dry-run 或 migration-only 参数，`NewServer` 会在 HTTP 服务开始监听前创建并启动后台任务。因此即使马上停止 HTTP 端口，也已经发生了数据库迁移和任务初始化。

演练至少要核对：

- 纯 SQLite、纯远端主库或混合副本的拓扑没有被启动配置改变。
- 账号、渠道、OAuth 和下游令牌可由目标密钥解开。
- `0` 天日志恢复、正常历史窗口和全量恢复分别符合预期。
- 未合并的计费事件仍在，结算回执没有重复扣费。
- 容器中的 `/app/data` 指向预期绑定目录或命名卷，UID 1001 可写。

## 执行升级

先进入维护窗口，停止入口流量和新请求，随后停止旧写入进程。对于 Compose 部署，`docker compose stop pivotflow` 足以停止该服务；不要执行 `docker compose down -v`，后者会删除命名卷。

准备并校验目标产物。自有二进制应核对发布页的 `checksums.txt` 和本地 SHA-256；容器应拉取完整标签，并记录它的 digest。保留旧二进制或旧镜像本地副本，不要先删除回退材料。

```bash
sha256sum -c checksums.txt --ignore-missing
docker pull "$TARGET_IMAGE"
docker image inspect "$TARGET_IMAGE"
```

`$TARGET_IMAGE` 应包含完整版本标签或 digest。若代理、镜像仓库或部署平台提供解析后的 manifest digest，把它与镜像标签的观察结果一起保存。不要用 `latest` 或 `beta` 的当前时间点替代这份记录。

保持原有 `SQLITE_PATH`、数据库 DSN、计费日志路径、副本开关、主密钥来源和文件所有权。替换程序后只启动一次目标版本，等待迁移、计费恢复和健康检查结束；失败时立即停止，不要反复启动猜测迁移是否完成。

## 升级后验收

| 观察项 | 成功标准 | 失败时优先检查 |
| --- | --- | --- |
| 程序版本 | 控制台和启动日志显示准确目标标签/提交 | 实际启动的旧进程、镜像 digest 或二进制路径 |
| 存储拓扑 | SQLite 或唯一远端主库与升级前一致；混合模式按要求启用 | 两个 DSN 同时存在、`SQLITE_PATH`、副本开关 |
| 主密钥 | 账号、渠道、OAuth、通知和 WebDAV 凭证可正常解密 | 密钥来源优先级、文件内容来源、版本是否匹配 |
| 计费 | 待处理数量合理，回执能继续结算且不重复扣费 | 是否混用了不同实例的 journal、回执或数据库时点 |
| 运行 | `/health`、登录、模型路由、令牌过滤和通知测试通过 | 启动日志、数据库迁移、文件权限和外部访问策略 |
| 权限 | `/app/data` 中数据库、WAL 和日志由可写用户持有 | 绑定目录所有权、UID/GID 1001、命名卷是否接错 |

升级后的首次备份应生成新的 WebDAV 校验证据。旧的 `last_sync_at` 只能显示为旧上传记录；只有完整的回读校验字段和最新同步时间一致时，页面才可以把记录标为已校验。

## 回退

迁移没有通用 down engine。注释说旧列被保留，也不能推导出任意旧程序都能读取新数据库；`debug_logs`、`admin_sessions`、`channel_url_states` 等表发生过重建或删除。目标版本一旦迁移数据结构或写入新语义，原地降级就是未验证操作。

回退应恢复一套相互匹配的旧状态：旧程序准确标签或 digest、升级前的数据库快照、同一时点的密钥与版本、启动配置、本地计费日志和结算回执。不要只换回旧镜像而继续使用已迁移的生产库。

升级后可能已经接受请求。回退前先统计这些请求的日志、令牌用量、待结算事件和已提交回执。直接恢复升级前数据库会丢掉这段记录；若要保留，应先完成结算和外部对账，或在隔离副本中验证能够把它们合并到回退状态。不能确认时，宁可先停止写入并人工核对，也不要重复恢复或重复导入。

回退完成后的验收与升级相同：程序版本、存储拓扑、主密钥、计费、路由和文件权限全部通过后再开放流量。清理旧产物前至少保留一个完整观察周期的日志、回执和备份证据。

## 不要这样做

- 不要把新二进制直接指向生产库并称为“无害迁移检查”。
- 不要执行 `docker compose down -v`，也不要在发布 Compose 与源码构建 Compose 之间直接换用数据目录。
- 不要把 `latest`、`beta`、分支构建或脏工作区当成可复现的精确版本。
- 不要在没有同点数据库、计费日志、回执和主密钥的情况下演练或宣称完成灾难恢复。
