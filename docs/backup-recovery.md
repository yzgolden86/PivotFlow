# 备份与恢复

本文面向需要恢复配置或整台实例的维护者。先确认要恢复什么，再选择路径。把 JSON 配置合并当成整库恢复，或只复制活动中的 SQLite 文件，都可能留下不一致数据。

| 目标 | 使用 | 能得到 | 不能得到 |
| --- | --- | --- | --- |
| 迁移站点、账号、渠道、令牌和设置 | 控制台 JSON 文件或 WebDAV 配置备份 | 按目标 ID 重映射后的可迁移配置 | 完整请求日志、用量历史、待结算记录、结算回执 |
| 恢复原实例的准确运行状态 | 同一时点的主库、本地计费日志、主密钥和启动配置 | 数据库中的运行记录与配置 | 仅凭任何一份文件都无法单独完成恢复 |

## 先确定恢复边界

JSON 格式版本为 `1.0`，范围是 `all`、`connections` 或 `settings`，控制台对应“全部配置”“连接与路由”“系统设置”。导出在主库的单个配置事务中读取配置，避免并发修改时混用不同时间的站点和账号；混合存储同样以主库为来源。

JSON 导入是合并和重映射，不是整库覆盖。账号、站点和渠道的身份会按规则匹配，旧 ID 只用于同一份文档内的引用。账号或渠道不可用时，相关绑定保持停用；目标中未被文档列出的绑定不会被删除。旧版 JSON 没有绑定清单时，沿用原有的人工接管规则，不自动猜测投影键或启动同步。历史上同一渠道存在多条绑定时，恢复停用渠道会将这些已有绑定全部设为人工接管并停用，保留本地绑定身份和同步历史；新文件携带的绑定仍需通过占用冲突检查。

绑定清单只携带 `site_account_id`、`channel_id`、`projection_key` 和 `pricing_group`。恢复后的绑定保存为人工接管状态。账号模型清单按导出账号整份替换，空清单也会清空该账号的模型；日常模型发现仍按独立语义运行。

备份不包含计费历史、支付或充值回执、待结算日志，以及请求日志、统计、余额每日快照和签到历史等运行数据。已有令牌的用量计数可能保留，但 JSON 无法重建丢失的历史令牌明文；这类条目会以警告或“保留”结果出现。

## 数据库必须成组备份

最稳妥的方式是正常停服，待所有写入结束后复制文件。不能停服时，必须为每个 SQLite 数据库分别取得一致快照；程序与计费日志默认使用 WAL，单独复制活动中的 `.db` 会漏掉尚未合并的写入。

一套完整恢复集合至少包含：

- 主数据库。纯 SQLite 实例是 `pivotflow.db`，远端主库是 MySQL/PostgreSQL 的同一时点备份或克隆。
- 每个实例各自的本地计费日志。默认名是 `billing-pending.db`；可通过 `PIVOTFLOW_BILLING_JOURNAL_PATH` 放在其他受控路径。
- 主库中的结算回执，即 `token_settlements`。计费日志与回执用于识别同一事件，避免恢复后重复扣费。
- 主密钥和版本：`FUSION_MASTER_KEY` 或 `FUSION_MASTER_KEY_FILE`，以及所设置的 `FUSION_MASTER_KEY_VERSION`。
- 受控保存的 `.env` 或启动配置，至少要能重建数据库 DSN、`SQLITE_PATH`、计费日志路径、副本开关和密钥来源。

计费日志使用 WAL 和 `synchronous=FULL`，恢复时仍应与主库及回执成组保存。多实例共用一个远端主库时，只恢复主库克隆不够；每个实例的本地计费日志都要纳入同一时点集合。详细密钥规则见[安全与备份](security.md)。

主库是配置的权威来源。启动恢复以主库查询结果重建 SQLite 副本；主库某个配置表查询成功且为空时，会在同一事务中清空副本对应表。该行为已用两套合成 SQLite 模拟验证，不能据此声称真实 MySQL/PostgreSQL 驱动和网络故障路径也已验证。

## JSON 恢复

1. 需要尽量少丢运行数据时，先进入维护窗口并停止写入，再备份当前数据库和计费日志。
2. 在控制台选择本地 JSON，或在已配置的 WebDAV 上生成恢复预览。预览会冻结输入；确认时不会重新读取本地文件或再次下载。
3. 检查冲突、停用、保留项、遗漏警告和绑定说明。存在冲突时整份配置不能应用。
4. 确认应用后读取同一预览状态。收到“结果待确认”时先核对，不要重新提交或立即导入同一文件。
5. 按账号、渠道、路由、令牌权限和通知分别做一次实际验证。认证通过或预览无冲突都不能代替这些检查。

具体匹配、模型和绑定语义见[配置导入与渠道同步](config-import.md)。

## WebDAV 上传证据

WebDAV 导出先在本地编码，超过 32 MiB 时在 PUT 前拒绝。服务对固定字节执行一次 PUT，成功后 GET 同一目标，并发送禁用缓存的请求头。只有完整长度和 SHA-256 都与发送内容一致，才算本次目标内容已验证。

回读最多 5 次，间隔 1 秒，整个回读阶段最多 10 秒。只重试读取；认证拒绝、HTML 响应和超大响应立即失败。PUT 返回 HTML 状态页不构成失败，最终以 JSON 文件的回读结果为准。失败不会删除远端文件，也不会推进“上次成功”或“上次校验”时间。

| 响应或记录 | 解释 | 操作 |
| --- | --- | --- |
| `status: success`、`verification` 完整、`metadata_saved: true` | 本次内容已校验，主库已保存记录 | 核对范围、遗漏警告及重新读取的记录；副本异常仍需单独处理 |
| `verification` 完整、`metadata_saved: false`，并提示状态未保存或待确认 | 内容已回读验证，但状态没有可靠保存 | 进程内先重试保存元数据；重启后这份内存观察丢失，下个正常周期会生成新备份 |
| `backup_config_changed` | 本次内容已校验，但上传期间连接设置改变 | 此回执属于旧目标，不会写入或继续重试新目标的记录；核对保存后的地址和凭据 |
| `backup_status_superseded` | 已有较新的上传或校验，或同一时间对应不同内容 | 较早回执不会覆盖或继续重试保存；核对最新持久记录 |
| 只有旧的 `last_sync_at`，没有完整校验证据 | 旧版上传记录，内容尚未经回读证明 | 重新执行备份并核对新证据 |
| `last_sync_at` 晚于 `last_verified_at` | 最新上传尚未校验，较早证据只能作为历史 | 重新执行备份以取得新证据，不能把旧摘要标成最新 |
| `verification.warning_count > 0` | 字节正确，但导出时遗漏了不可恢复条目 | 回到 JSON 警告和恢复预览核对，不能把字节校验当作全部可恢复 |

保存校验状态前会复核 WebDAV 目标、用户名和密码指纹。设置已变化时，不会把旧目标的结果记到新目标，也不会覆盖新设置。主库已提交但副本同步失败时，响应区分“内容已验证”和“副本异常”；不要因保存警告自动再次 PUT。

重新保存相同的明文密码会保留其加密封装和校验记录。旧封装无法解密时，明确提交的新密码可在当前主密钥下重新加密；恢复文件中的替换密码也遵循此规则。没有可用的当前主密钥或没有提供替换密码时，无法解密的恢复配置仍会被阻止。

控制台分别展示“已保存的校验记录”和必要时的“本次上传的校验回执”。后者只在当前页面保留，不代表当前设置已有同一条持久记录。比较两份证据时核对时间、完整大小、摘要、备份范围和警告数；字段不同就保留独立回执。证据缺字段、不是完整毫秒时间、摘要无效或同步时间早于校验时间时，记录显示为“需核对”。新的内存校验待保存时，旧的持久摘要明确标为历史。最近一次上传失败会保留此前成功的证据，并显示安全错误说明；仅重试元数据或确认已有完整证据时也保留这个后续失败记录。

服务不删除远端旧文件，也不创建版本历史。上传失败后的清理、旧版本保留和多设备冲突处理由 WebDAV 存储侧负责。

## 整台实例恢复

1. 在副本或隔离恢复环境选择同一时点的数据库、计费日志、回执、密钥和启动配置。
2. 使用明确配置的 `SQLITE_PATH`，避免默认目录不可写时回退到系统临时目录。纯 SQLite、单一远端主库和“主库 + 本地副本”分别按原拓扑恢复。
3. 远端主库使用隔离克隆；副本由当前程序从主库重建。不要手工混用不同实例或不同时间的计费日志。
4. 启动隔离副本，验证主密钥可解开凭证、结算待处理数量合理、历史窗口符合 `PIVOTFLOW_SQLITE_LOG_DAYS`、令牌和渠道路由可用。
5. 隔离验收通过后才切换真实服务。切换后保留旧程序、旧数据库和旧密钥，直到观察期结束。

主启动路径会执行迁移和后台任务，没有 dry-run 或“只迁移”开关。不要把新程序直接指向生产库来试探迁移是否成功；先使用数据库副本和隔离网络。

恢复后按下表核对实际结果，不能只看进程是否启动：

| 检查 | 通过条件 |
| --- | --- |
| 站点与账号 | 归属正确，目标无关记录没有被导入覆盖 |
| 模型与绑定 | 模型清单符合备份；绑定引用已重映射并处于预期的停用/人工接管状态 |
| 凭证 | 账号、渠道、OAuth、通知和 WebDAV 凭证可由目标密钥解开 |
| 令牌与路由 | 摘要、权限、渠道限制和协议过滤可实际生效 |
| 计费 | 待处理事件与回执能对账，测试请求没有被重复扣费 |
| 副本与历史 | 混合副本按主库重建；日志窗口符合配置，未把缺失历史当作已恢复 |

## 真实数据演练

演练只使用复制出的数据库、计费日志和密钥，以及隔离的数据库/WebDAV 克隆。具体控制如下：

- 断开测试实例对真实上游、通知、WebDAV 和支付系统的外部访问，只放行测试所需的本机路径或专用克隆。
- 测试数据库和远端库使用独立凭据，不共享生产账号；禁用或改写会触发外部任务的测试配置。
- 先记录源和目标的行数、关键摘要、计费待处理数和校验时间，恢复后再比较。
- 让测试服务至少完成一次启动、一次配置读取和一次受控停服，确认没有向生产外部目标发请求。
- 演练结束保留结果和安全摘要，销毁测试实例，不复用测试数据库写回生产。

本文没有声称已完成真实 MySQL/PostgreSQL、真实 WebDAV 或线上切换演练。这些必须由目标部署环境按上述控制逐项验收。返回程序升级时使用[升级与回退](upgrade.md)。

## 本地合成验证

以下命令使用测试自有临时数据库，不启动服务，也不连接真实数据库或上游：

```bash
export FUSION_MASTER_KEY="$(printf '%s' '0123456789abcdef0123456789abcdef' | base64)"
export FUSION_MASTER_KEY_VERSION=phase-synthetic
export PIVOTFLOW_PASS=synthetic-phase-validation
export PIVOTFLOW_TEST_MYSQL_DSN=
export PIVOTFLOW_TEST_POSTGRES_DSN=
go test -tags sonic -buildvcs=false -count=1 ./internal/app ./internal/storage ./internal/storage/sql -run 'TestBackupRestore|TestBackupVerificationMigration|TestSyncManagerRestoreTable|TestRestoreSiteAccountModels'
```

这里使用公开的合成测试密钥，防止测试读取部署环境的默认密钥文件。Windows PowerShell 可在临时验证进程中设置同样的环境：

```powershell
$env:FUSION_MASTER_KEY = [Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes('0123456789abcdef0123456789abcdef'))
$env:FUSION_MASTER_KEY_VERSION = 'phase-synthetic'
$env:PIVOTFLOW_PASS = 'synthetic-phase-validation'
$env:PIVOTFLOW_TEST_MYSQL_DSN = ''
$env:PIVOTFLOW_TEST_POSTGRES_DSN = ''
go test -tags sonic -buildvcs=false -count=1 ./internal/app ./internal/storage ./internal/storage/sql -run 'TestBackupRestore|TestBackupVerificationMigration|TestSyncManagerRestoreTable|TestRestoreSiteAccountModels'
```

这些命令应在单独的测试终端执行，不复用该终端启动实际部署。它们覆盖两套磁盘库及密钥间的恢复、校验字段迁移、副本空表恢复和账号模型替换。模拟 WebDAV 的成功、失败、取消与竞争回归另用 `-run 'Test.*WebDAV|TestBackupSnapshot|TestBackupReview'` 执行，其中审查回归验证新记录优先、完整证据比较、相同或替换密码和历史共享绑定。测试通过只证明这些受测路径，不代表真实 MySQL/PostgreSQL、WebDAV 服务或整机灾难恢复已通过演练。阶段证据见[恢复验证记录](superpowers/plans/2026-11-22-backup-recovery-verification.md)。
