# 可靠结算与流式恢复

本阶段加固成功调用的 Token 累计用量与费用、认证 HTTP 跳转，以及 Responses 流中断的识别。请求日志和失败统计仍使用原有机制，不应视为财务流水。请求费用的来源、估算覆盖和上游对账边界见[费用来源与数据语义](cost-semantics.md)。

## 成功调用如何结算

请求完成时，网关生成一个固定 ID 的结算事件，保存 Token 哈希、发生时间、用量和本次已确定的价格，不包含原始 API Key 或请求正文。内存软限额立即累加一次；后台重试不重复累计内存费用。

事件先写入独立 SQLite 文件 `billing-pending.db`（WAL、`synchronous=FULL`）。后台在主库同一事务中写入 `token_settlements` 回执并累计 Token 费用、次数和用量。同一 ID、同一内容重试只结算一次；相同 ID 对应不同内容会报错并保留记录。混合存储还要把主库权威统计同步到 SQLite 副本，之后才删除待结算事件。

数据库提交成功但确认消息丢失时，事件仍会重试，回执阻止重复扣费。启动时先补齐旧事件、重新加载费用限额，再开放监听；恢复失败则启动失败。每轮启动恢复预算为 30 秒，已经确认的事件会被移除，大量积压可在修复故障后的再次启动中继续推进。

本地免费倍率为 0 时仍记录次数和用量；Key 倍率优先于渠道倍率。站点价格估算保留现有金额口径，不再重复乘本地倍率；这不等于上游账单已经确认。费用限额仍是完成后计费的软限额，不能保证并发请求的精确预留，也不是跨实例共享的钱包。

同一次成功请求的日志费用和 Token 结算尝试使用同一次已解析的费用快照，但两者都属于本地记账口径。旧日志、旧结算回执和已有累计用量不会被新费用状态重新定价、补算或迁移。金额未知、部分或非法时仍需保留已经确认的成功用量，不能把“未知费用”当作免费或未发生调用。

上游费用为负数、非有限值或超出微美元整数范围时，保留正常用量，把本笔金额置零并在待结算记录和主库回执标记 `cost_invalid=true`。同时记录含事件 ID 和原因的 ERROR，累计 `invalid_cost_events`；它表示金额未知，需要核对，不能当作免费调用。请求日志以 `cost_status=invalid` 标记这类金额，不把它计入完整估算。持久化层仍严格拒绝非法数值，异常金额不会使整个网关持续 503。对照上游账单核对 `token_settlements WHERE cost_invalid = 1`；本阶段没有自动补扣功能，这部分费用可能被低估。原有未知模型定价、负用量的零价告警口径保持原样。

## 数据文件与备份

- 默认位置是 `SQLITE_PATH` 同目录下的 `billing-pending.db`；未设置 `SQLITE_PATH` 时是 `data/billing-pending.db`。
- 可用 `PIVOTFLOW_BILLING_JOURNAL_PATH` 指定文件路径。URI 或内存形式的 `SQLITE_PATH` 需要显式配置独立持久文件。
- MySQL/PostgreSQL 部署也需要本地持久卷；各实例保留自己的文件，不能随容器重建丢失，也不能与主库或 SQLite 副本使用同一文件。
- 待结算文件固定使用 WAL，不跟随主库 `SQLITE_JOURNAL_MODE`。放在支持 SQLite WAL 的本地文件系统；容器应挂载持久卷。
- 正常停服后备份主库、待结算文件和凭证主密钥，恢复时成套使用同一时点的数据。JSON 配置导出不包含计费运行状态。

`token_settlements` 回执会随成功调用持续增长，本阶段没有自动裁剪。直接删除回执会使旧 journal 或旧备份再次重放时重复结算。`billing-pending.db` 及运行期的 `-wal`、`-shm` 文件也不属于可删临时文件。停服、备份细节见 [安全与备份](security.md)。

## 故障时的行为

| 状态 | 行为与恢复 |
| --- | --- |
| 主库暂时不可用 | 事件已保存到本地，后台重试；本进程内存限额继续累计，重启后补账 |
| journal 不能写入 | 保留尚未保存的在途事件，并尝试直接写主库；暂停新的代理工作，HTTP 返回 503 与 `Retry-After: 5`，WebSocket 的下一回合返回 503 `billing_unavailable` |
| journal 恢复 | 先补存内存事件，再执行真实写入探测；成功后恢复准入，管理接口在故障期间仍可用于排障 |
| Token 在请求途中被删除 | 事件终结并计入删除 Token 指标，不重新创建 Token |
| 优雅关停 | 等待已准入工作完成，尝试有限时间刷入主库；已持久的积压留到下次恢复 |

成功事件的保护从完成回调创建并保存记录开始。上游已发生费用但进程在完成回调前崩溃、存储设备丢失、或者 journal 与主库同时不可写后强制杀进程，都不在可恢复保证内。在途事件仍仅位于内存时，应先恢复存储并确认 `unpersisted=0`，再关闭进程。

## 运行指标

管理员接口 `GET /admin/runtime-metrics` 新增 `billing` 对象，原有 `responses_websocket` 保留。它只提供聚合计数，不返回 Token 哈希、事件 ID 或凭据。

| 字段 | 含义 |
| --- | --- |
| `enabled` | 当前 Server 是否已启用持久结算；正常生产入口始终启用 |
| `pending` | 最近观测到的 journal 待确认数量，重试周期会重新校准 |
| `unpersisted` | 仍只在内存中等待保存的事件数量，应优先处理 |
| `blocked` | journal 故障或正在关停，停止准入新代理工作 |
| `journal_failures` / `store_failures` | 本进程累计失败次数；恢复后不会清零 |
| `invalid_cost_events` | 本进程创建的金额无效事件数；重试不重复计数，主库 `cost_invalid` 标记跨重启保留 |
| `settled` / `deleted_token_events` | 本进程处理确认次数／Token 已删除的事件处理次数，重放确认不等于新增消费 |
| `last_success_at` | 最近完成处理的 Unix 毫秒时间；初始为 0 |

`token_failure_stats.queued/dropped` 对应原失败统计队列；它的丢弃计数不再包含成功结算事件。[请求身份与尝试历史](request-history.md)现已接入，并提供独立 `request_traces` 队列指标。[后台运行健康](runtime-health.md)在首页和独立详情中展示结算文件访问、主库结算、最老积压、当前故障与历史失败；刷新失败或快照过期时显示未知，已发生的记录损失和副本差异继续保留。

## 认证跳转与流式边界

携带认证的上游 HTTP 和站点 Provider 请求只跟随同源跳转：协议、主机名和有效端口必须一致。主机名不区分大小写，省略默认端口与显式 `:80`/`:443` 等价。最多跟随 10 次跳转，拒绝 URL userinfo。Provider 原有地址与 DNS 校验继续执行，已有拒绝所有跳转的 OAuth/账单客户端保持严格策略。

301/302 按 Go HTTP 标准处理，POST 可能转为 GET；307/308 在请求体可重放时保留方法和正文。配置上游时应直接填写最终源站地址，跨域、换端口或 HTTPS 降为 HTTP 的跳转将报错。

Responses SSE 已出现 `response.*` 事件但未出现终止事件就结束时，网关记录 599 流不完整。输出已经交给客户端后，不重放或拼接另一个上游的结果。客户端主动取消仍按 499 处理，不冷却渠道；WebSocket 切换 HTTP 时沿用完整 transcript，旧物理 WebSocket 的 `previous_response_id` 不会带入新传输。

检测器逐块扫描 data 顶层 `type`，同时识别 `event:`，支持 `type` 在超大 JSON 后部以及字段跨读取块的情况；行缓存最多 64 KiB、JSON 标识 token 最多 64 字节，不缓存完整事件。识别终态包括 `completed`、兼容的 `done`、`incomplete`、`failed`、`cancelled` 和 `canceled`。这是对现有协议恢复约定的回归加固，没有把所有协议转换成统一的重放机制。
