# 路由与分发

## 路由流程

```text
下游请求
  -> 读取模型与客户端协议
  -> 构建可用渠道快照
  -> 过滤成本上限和冷却项
  -> 按优先级/健康策略选择渠道
  -> 选择 URL 与 Key
  -> 必要时协议转换
  -> 失败分类、冷却、切换或返回
```

选择器、Key/URL 调度、冷却管理和协议转换是这条链路的核心；站点控制面只负责把账号投影成渠道，不参与这条热路径。

## 渠道选择策略

系统设置 → 路由策略 → “渠道选择策略”（`route_strategy`）决定同一模型有多个可用渠道时如何挑选。两种策略都**先比优先级**，只在优先级相同的渠道之间才有区别。

**均衡轮询（`balanced`，默认）**：同优先级内按权重平滑轮询，权重为有效 Key 数（总 Key 数减去冷却中的 Key）。每个请求换一个渠道。五个等权渠道会得到 `41 44 45 46 47` 的完整轮转；权重为 3:1:1:1:1 时，高权重渠道的三次机会是分散开的（第 1、4、7 位），不会连着命中。

**粘性轮询（`sticky`）**：固定使用上次成功的渠道，直到它失败才切换。粘性记录按模型独立保存，渠道失败、被跳过（Key 全冷却、达到 RPM 或并发上限）或被删除时立即清除，另有 30 分钟有效期，避免长期空闲的模型被钉在一个可能已经变慢的渠道上。

选择建议：默认用均衡轮询。粘性轮询在上游有会话亲和或缓存命中收益时更划算，但它会把流量集中到少数渠道，而中转站的风控通常按**单账号**的请求模式打分而不是看总量，风险高于均衡。要用粘性，建议同时给该渠道配一个 `rpm_limit` 硬上限。

改这一项**需要重启进程**才生效：策略在启动时读入内存，运行期不重新读取配置。

无论哪种策略，一次请求内部的失败回退行为都一样：选择返回的是一个有序候选列表，首个是本次选中的渠道，其余按顺序作为失败回退。首选失败且错误性质允许换渠道时，当场顺着列表继续尝试，这个过程不推进轮询游标。下一个请求才按策略推进。

## 渠道字段

- **优先级**：用于候选排序；数值越高越优先。
- **Key 策略**：顺序、轮询等策略控制同渠道多 Key 的选择。
- **URL**：可以配置多个 URL，支持按 URL 声明上游协议。
- **协议模式**：`auto` 自动协商，`upstream` 只走原生协议，`local` 只走本地转换。
- **模型映射**：左侧是对外模型，右侧可指定实际上游模型。
- **倍率/限额**：成本倍率、日成本、RPM 和并发分别作用于统计或调度。
- **高级请求设置**：折叠区，默认不改变任何请求。支持按顺序覆盖、追加或删除上游请求头，以及用点分路径覆盖或删除请求体 JSON 字段（例如 `temperature`、`metadata.user`）。认证头由系统托管，不能从这里覆盖，请求头值也不允许出现换行。普通请求头本来就会按安全策略透传，协议转换选“上游原生”即可做协议级透传——只有确实需要改写上游请求时才用这里。

## 模型统一映射

不同站点对同一个模型的命名往往不一致：`GLM-5.2`、`glm-5.2`、`z.ai/glm-5.2` 可能指同一个模型。系统设置 → 路由策略 → “模型统一映射”（`model_alias_groups`）可以给它们一个统一入口：客户端请求统一名称，系统按每个渠道实际存在的模型名发送，候选池是各别名对应渠道的并集。

配置方式有三种，通常不需要手打：

- **套用建议**：面板顶部会列出自动检测到的可合并组。检测只归并那些仅在大小写、分隔符（`.` `_` `-`）、厂商前缀（`z.ai/`）、日期后缀（`-20250219`，可带构建号）或 `latest` 后缀上不同的名字，点“套用”即写入。有意义的变体不会被合并——`gpt-5.6` 与 `gpt-5.6-sol`、`claude-opus-5` 与 `claude-sonnet-5`、`glm-5.2` 与 `glm-5.2-air`、preview 版本都会保持独立。
- **从渠道挑选**：搜索式多选，列出每个模型在几个渠道存在、都在哪些渠道、是否已被映射。跨多次搜索的勾选会保留，可以搜 `gpt` 勾几个再搜 `gemini` 勾几个。
- **直接粘贴**：展开某条映射后，在文本框里每行一个上游名称。

映射条目默认折叠成一行，超过四条时出现搜索框；「批量创建」在二级界面里从检测建议中挑选组合，确定后一次写入。

两点必须注意：

- 上游名称是**精确匹配**的：`GLM-5.2` 和 `glm-5.2` 是两个不同的路由键，两个都要列进同一组，只写一个不会自动兼容另一个。
- 改完**需要重启**才生效。未配置任何映射时（默认值 `[]`），路由行为与之前完全一致。

映射还影响两个外围环节，保持同一口径：

- **下游模型列表**：`/v1/models` 等列表端点把组内名字折叠成统一名称展示，别名不再出现在列表里，手动输入仍可请求。
- **令牌模型白名单**：白名单按映射组求值——`allowed_models` 写了组内任一名字（统一名称或别名）即放行整组，不会再出现「别名能请求、统一名称被拒、列表不显示」的口径分裂。

## 同一渠道上存在多个别名时的选择顺序

轮询发生在**渠道之间**，别名不参与轮询：别名只决定哪些渠道进入候选池，选中渠道后由 `actualModelFor` 决定实际发送哪个名称。它按顺序尝试统一名称和组内各别名，取第一个在该渠道上存在的名字。

边界情况：如果**同一个渠道**同时配置了组内多个名称，而这些名称在该站点有不同的计费倍率（例如 `773/minimax-m3` 与 `minimaxai/minimax-m3` 单价不同），实际用哪个由它们在映射组里的**填写顺序**决定，不会自动选便宜的那个。想控制成本就把单价低的排前面；如果该渠道的倍率对所有名称一致，则顺序无所谓。

## 冷却与故障切换

认证失败优先冷却当前 Key；模型不可用、超时和流中断通常冷却模型；网络不可达冷却渠道或 URL。冷却状态在渠道列表和请求日志中可见。系统支持自定义冷却探测规则，但个人部署应先使用内置分类器。

## 站点账号投影

“同步站点渠道”会读取账号的基础 URL、可用模型和路由 API Key，按 `projection_key` 建立来源绑定。同步是幂等的：重复同步不会无条件创建重复渠道。

如果一个站点有多个分组：

1. 在上游为每个分组创建独立模型 API Key。
2. 在站点账号或投影设置中为每组使用不同的投影键。
3. 同步后在渠道页分别设置优先级、模型限制或访问令牌的渠道限制。

不要把“上游管理令牌”当作模型 API Key 投影。没有可用模型 Key 时，系统会返回 `routing_api_key_unavailable`，而不是把管理令牌冒充成路由凭证。

## 何时用手工渠道

手工渠道用于 Provider 没有账号适配器、一个逻辑渠道需要多个自定义 URL、或你明确希望完全手动管理 Key/模型。手工渠道和站点投影可以同时存在，靠名称、优先级和模型范围区分；不要为同一个账号同时创建一条手工渠道和一条投影渠道，除非你确实需要不同的路由策略。
