# 请求身份与尝试历史

控制台「请求日志」默认打开「完整请求」。一行对应一次 HTTP 模型调用，或一个进入执行器的 Responses WebSocket 回合。原有日志位于「上游日志」，「进行中」继续显示活动请求。

## 定位一次调用

HTTP 代理响应带有 `X-PivotFlow-Request-Id: pf_req_…`。复制该 ID 到完整请求的搜索框，可查看最终结果和按执行顺序排列的尝试。网关生成 ID，客户端或上游提供的同名 Header 无法覆盖。上游日志和活动请求中的 ID 也可跳转到请求详情。

记录在调用结束后异步保存，通常会有短暂延迟；进行中的请求详情可能还不存在。历史记录已经过期、写入失败或队列丢弃时，也可能无法查到。旧版本日志没有这一身份，不会被推测拼接成请求历史。

[模型路由工作台](model-routes.md)可以按原始请求模型、客户端协议和令牌范围进入历史。「精确请求模型」与普通搜索分开，列表与汇总使用相同精确条件；筛选、页码和详情保存在 URL，浏览器后退可恢复。当前映射不会改写过去的请求身份。

WebSocket 每个回合有独立 ID，与 `Session-Id` / `Thread-Id` 的会话身份分开。ID 可从活动请求、上游日志或完整请求页获取；网关不会向 Responses 连接插入额外事件。

## 时间线表达什么

每个事件保存渠道名称、Key 序号（OAuth 显示为 OAuth）、配置 URL 序号、端点 origin、实际模型、上游协议和 HTTP / WebSocket 传输。还包括开始时间、耗时、首字耗时、状态、是否发起上游、重试方向与冷却决策。冷却的精确截止时间仅在决策提供时显示；否则不猜一个时间。

时间线会记录协议协商、`stream_options` 兼容重试、Codex 请求兼容重试、WebSocket 握手回退和重连。未能选出 Key 或协议、渠道限流等本地跳过有明确标记，不计为已发起的上游尝试。HTTP 同源重定向属于一次 HTTP client 调用，当前不逐跳展开。

“响应已开始”表示已经向客户端输出，失败后不能把整段请求再发一次。流可能已返回 HTTP 200，却以内部状态 `597`（流错误）、`598`（首字超时）或 `599`（流不完整）结束；详情中的最终状态表达网关语义结果，不是声称线路上发送了该 HTTP 状态码。`499` 客户端取消独立计数。上游返回的 499 仍是失败，不当作客户端取消。

总耗时从进入处理器/回合执行器开始；全局等待只统计获取全局并发槽的时间，不包含鉴权中间件、WebSocket 回合锁等外层等待。一次尝试的耗时独立记录，不能与原有累计到渠道的日志耗时直接相加比较。

最多保存 128 条事件，超出后详情明确显示截断，完整尝试计数继续累计。最后可见事件可能并非最终尝试；最终结果以上方摘要为准。

## 两种成功率

- 客户端成功率 = 最终成功请求 ÷（最终成功 + 最终失败）。客户端取消单列，不进入分母。
- 上游成功率 = 成功上游尝试 ÷ 已发起上游尝试。包含实际发出的能力协商、兼容重试与 WebSocket 握手；本地跳过不进入分母。

例如一次调用先返回 429，再切换渠道成功：最终成功请求为 1，上游尝试为 2，上游成功为 1。两种口径用于回答不同问题。健康排序仍沿用原有规则；费用不由成功率推导，按请求发生时保存的来源、状态和计费方式解释，见[费用来源与数据语义](cost-semantics.md)。

这些数值只覆盖当前筛选范围内**已保存的请求摘要**。手动渠道检测、定时巡检、模型列表和本地 token 计数不会混入完整请求统计。鉴权中间件拒绝、WebSocket 帧归一化或回合锁之前的拒绝尚不属于该记录范围。

请求历史是路由和协议观测，不是费用明细或上游账单。普通日志中的费用快照和 Token 本地记账分别负责单请求解释与软限额累计；请求历史不会用上游尝试次数、余额变化或当前价格反推某次请求的真实扣费。

## 缓存请求

[可选请求缓存](request-cache.md)会在摘要和详情中保存固定代码 `cache_status`／`cache_reason`，解释命中、未命中、刷新、绕过及未保存的原因。旧记录为空，界面不会推测补齐缓存状态。

完整写出的命中仍是一次客户端成功请求，拥有新的网关请求 ID；真实上游尝试为零，空时间线属于预期结果，不新增上游 tokens 或费用。网关不添加一条虚构的上游日志。缓存内容原样保留此前 JSON 的 `usage`，下游 SDK 应结合缓存响应头区分复用与新调用。

找到缓存但写出失败或客户端取消时，详情明确说明响应未完成，不记为成功请求。缓存标记与上游尝试数矛盾、原因未知或计数缺失时，不据此推断调用或费用。

## 数据与访问

`request_traces` 表以请求 ID 为主键，摘要与尝试 JSON 同一行写入，重复写入不会重复统计。普通 `logs` 表增加 `request_id` 和 `attempt_number` 关联字段。启动时自动进行增量迁移，既有日志保留；普通日志保留期也应用于请求历史。

时间线不保存 Key 内容或哈希、HTTP Header、URL userinfo/path/query、提示词、响应正文或任意上游错误文本。原因采用固定代码；「复制诊断 JSON」仅复制这些结构化字段。管理员配置的渠道名、模型名和端点 origin 会包含在诊断中，分享前仍可自行去掉这些部署标签。

管理接口需要管理员身份。Token 自助接口在数据库查询中强制绑定该 Token，并隐藏渠道、Key、URL 和实际上游模型等路由细节。读取其他 Token 的 ID 与读取不存在的 ID 均返回 404。

| 只读接口 | 内容 |
| --- | --- |
| `GET /admin/request-traces` | 请求摘要列表 |
| `GET /admin/request-traces/stats` | 同一过滤条件下的两种口径计数 |
| `GET /admin/request-traces/:request_id` | 摘要与尝试详情 |

列表与统计接受 `range`、`search`、`outcome`、`auth_token_id`、精确 `model` 和精确 `client_protocol`；列表另有 `limit`、`offset`。自助接口使用 `/dashboard/request-traces` 对应路径，查询参数不能扩大 Token 身份范围。精确模型最多 191 字符，拒绝超长名称、控制字符、重复参数及无效协议；较长工作台模型使用普通历史入口并明确这一存储边界。

## 故障与运行指标

请求历史是可降级的观测数据。独立队列最多 256 条，批量写入最多 32 条，失败最多尝试三次，单次写入截止时间 3 秒。队列满、最终写入失败或进程在刷盘前退出时可能丢记录；它不承担[成功计费 journal](reliability.md)的财务持久化保证。

`GET /admin/runtime-metrics` 中 `request_traces` 提供 `queued`、`capacity`、`buffered`、`dropped`、`write_failed`、`written`、`last_dropped_at` 和 `operation`。`buffered` 包含已取出但尚未完成写入的批次；累计计数重启清零，`written` 表示写入调用成功处理的条目数，不代表去重后的全库记录数。

混合模式先保存 SQLite，再异步同步主库。`request_traces.replication` 提供远端同步队列容量、积压、丢弃及失败计数，以批次为单位，积压包括正在执行的批次；容量限制独立于普通日志，避免大时间线挤满同步队列。主库暂时失败可能使远端副本缺记录，本地仍可读；重启恢复合并远端已有记录，保留尚未同步的本地记录。仅备份远端主库无法保证包含这些本地记录。

[后台运行健康](runtime-health.md)已提供首页摘要和独立详情；写入恢复后仍保留累计丢失记录，并将主库复制状态独立呈现。[站点维护任务](site-tasks.md)、[客户端接入](client-connection.md)与[请求缓存](request-cache.md)均连接到相应的运行观察或请求记录。
