# 费用来源与数据语义

PivotFlow 的请求费用是可追溯的价格估算，不是上游发票，也不是已经对账的账单。由于价格目录、站点定价、渠道倍率、工具调用和上游计费口径可能不同，同一个页面上的金额和 Token 累计费用需要分开理解。

本阶段在请求发生时保存费用解释快照，让请求日志、概览、统计和令牌页面使用同一套来源、状态和计费方式。它不会重新解释旧请求，不会修改已经保存的费用金额或财务回执，也不新增上游对账调用。

## 四种不同口径

| 口径 | 含义 | 不应被当作 |
| --- | --- | --- |
| 请求费用估算 | 请求发生时按可用站点价目或本地公开价计算出的金额 | 上游账单、已确认扣费 |
| `recorded_cost_usd` | 当前筛选范围内，按日志保存的倍率计算的安全有效记账金额合计 | 真实上游消费 |
| Token 本地记账 | `token_settlements`、令牌累计费用和费用软限额使用本地结算结果 | 跨实例钱包、精确预留 |
| 上游账单 | 上游供应商最终结算的金额和币种 | 当前功能尚未接入 |

请求日志中的费用来源和状态用于解释“这个数字如何得到”。余额是账户资产观察值，不能反推某一次请求的费用；日志与汇总也不会用余额变化倒推扣费。

## 费用来源

`cost_source` 说明模型金额的主要依据：

| 来源 | 含义 |
| --- | --- |
| `site_pricing` | 使用站点价目表；其中已有分组倍率，不再乘本地渠道或 Key 倍率 |
| `local_estimate` | 标准金额来自本地公开价目；有效记账另应用请求时本地渠道/Key 倍率 |
| 空值或历史无效值 | 旧记录或无法识别来源；不能猜成站点价格 |

`site_pricing` 和 `local_estimate` 都只是估算。站点价目可能包含上游或中转站的分组规则，本地价目可能来自公开标价；两者都不代表上游已经按该金额结算。

本地渠道倍率明确为 `0` 时，本地有效记账为零，状态为 `local_free`；标准金额 `cost` 可以为正，`effective_cost` 和有效记账为零。这只说明 PivotFlow 的本地计费规则，不说明上游免费。`zero_price` 只表示价格与用量本身算出了零，不能与本地倍率免费混用。站点价格估算继续使用站点给出的金额口径，不额外乘本地倍率。

站点模型费与本地工具费同时存在时，模型部分保留站点来源，计费方式为 `mixed`。工具费来自本地估算，会在安全明细中与模型费分开。

混合费用仍先按既有算法计算 `cost = model_cost_usd + tool_cost_usd`。站点来源的有效记账等于该总额；本地来源的有效记账等于总额乘请求时倍率，负倍率沿用 `1`。拆分明细不会改变已保存的金额或对工具部分额外施加倍率。

## 计费方式

`cost_basis` 说明金额需要什么计费依据：

| 方式 | 含义 |
| --- | --- |
| `token` | 按输入、输出、缓存等 Token 用量计算 |
| `per_call` | 按次固定价格计算，不要求 Token 数 |
| `mixed` | 模型费和工具费等多个部分组成 |
| `unknown` | 没有足够依据确认计费方式 |

按 Token 计费需要可用的计费用量。全零用量本身不能证明请求免费；如果价格存在但没有可用于计费的用量，状态为 `usage_missing`，金额显示为 `—`。如果所有可用的计费 Token 计数都为零，同样不能把它说成“有收费 Token 证据”。按次模型不需要 Token 数也能得到完整估算。

工具调用费属于本地费用明细。模型费为站点价、工具费为本地估算的混合结果会以 `mixed` 明确标出。模型没有价格或用量的情况下，只有工具费等已知部分会计入 `partial_cost_usd`，状态为 `partial_estimate`。只有全部组成都有可靠依据时才是完整估算；不能把部分金额写成完整金额。

`mixed` 描述模型与工具等计费组成，不保证每一部分都已估出。模型金额未知而工具费已知时，仍用 `mixed` 配合 `partial_estimate`，金额只包含已知部分。

## 费用状态

`cost_status` 描述金额是否完整、为零或无法解释：

| 状态 | 含义 |
| --- | --- |
| `estimated` | 有价格依据和必要用量或按次依据，金额是完整估算 |
| `zero_price` | 请求发生时的可用价目和用量计算结果为零；不是未知，也不是已对账 |
| `local_free` | 本地渠道倍率明确为零；有效记账为零，不表示上游免费 |
| `usage_missing` | 有按 Token 的价格，但没有可计费用量；零金额不能解释为免费 |
| `unpriced_model` | 请求发生时没有可用的模型价格，无法完整估算 |
| `partial_estimate` | 工具等部分金额已知，但模型金额仍缺少价格或用量；只展示已知部分 |
| `invalid` | 数量或金额为负数、非有限值或无法安全处理；不输出非有限 JSON 金额 |
| `historical_unknown` | 旧行或未知元数据版本；金额保留，但历史依据不完整 |
| `not_charged` | 非 2xx 结果，网关没有按成功请求记账；不推断上游是否收费 |

页面会同时显示金额和文字状态。`$0.0000` 只在状态明确为零价或本地免费时代表已知零；`usage_missing`、`unpriced_model`、`invalid` 显示 `—`。历史正金额保留并说明依据不完整；没有依据的历史零金额显示 `—`。

成功请求先排除非法数量、金额和倍率，再判断本地倍率免费、部分估算、未定价、缺用量和完整零价。站点来源不会因为本地倍率为 `0` 而变成本地免费。`local_free` 的可知零金额只针对本地记账，完整覆盖说明仍不代表上游账单已确认。

普通失败请求标为 `not_charged`。费用汇总只统计成功 2xx 请求，失败记录不会混入成功请求数或估算覆盖率。

常见的日志读法：

| 示例 | 含义 |
| --- | --- |
| `$0.0012 · 本地公开价估算 · 按 Token` | 完整本地估算 |
| `$0.0000 · 本地记账免费（上游费用未确认）` | 本地倍率为零，不是上游免费 |
| `— · 未获取计费用量` | 有按 Token 价格但缺少计费用量，不能当作零价 |
| `$0.0040 · 部分估算` | 工具费等已知部分已计入，模型金额仍不完整 |
| `$0.0020 · 历史记录，依据不完整` | 旧金额保留，但没有可信的历史来源和明细 |
| 失败请求 | 显示未按成功请求记账，不进入成功费用汇总 |

## 请求时快照与历史记录

新请求保存 `cost_metadata_version=1` 的费用快照，包括来源、状态、计费方式和安全数值明细。价格目录后来变化、当前站点分组调整或模型下架，都不会重算这条历史记录。数据面板不会用今天的本地目录重估旧金额。

旧请求的 `cost_metadata_version=0`。升级只增加字段，不给旧请求补算价格、不修改原有 `cost`，也不伪造旧请求的“零价”“完整估算”或上游确认证据。旧成功行读取时归类为 `historical_unknown`，原有金额字段保留，但依据不完整；旧金额不能当作已确认免费或完整估算。历史零金额没有可验证依据时显示 `—`。

旧来源为空或无法识别时也不会猜成 `site_pricing`。历史安全明细缺失时留空，不能用今天的本地公开价冒充当时的站点明细。

读取日志时，非 2xx 结果优先显示 `not_charged`；版本 `1` 且状态在允许列表中使用已保存状态；其他成功行显示 `historical_unknown`。读取逻辑不会临时查询今天的价格目录来“修正”状态、明细或金额。

## 汇总、覆盖与对账

费用汇总从日志数据按同一筛选条件聚合，不加载完整日志，也不访问上游。概览快照的 `cost_summary`、`/admin/stats` 与 `/dashboard/summary` 响应使用同一查询；下游令牌只能看到强制绑定到自身令牌的范围，费用筛选不能扩大权限。

汇总 JSON 固定包含以下字段：

```json
{
  "version": 1,
  "currency": "USD",
  "reconciliation": "not_reconciled",
  "successful_requests": 0,
  "estimated_requests": 0,
  "zero_requests": 0,
  "local_free_requests": 0,
  "partial_requests": 0,
  "unknown_requests": 0,
  "historical_requests": 0,
  "site_pricing_requests": 0,
  "local_estimate_requests": 0,
  "mixed_requests": 0,
  "recorded_cost_usd": 0,
  "estimated_cost_usd": 0,
  "partial_cost_usd": 0,
  "historical_cost_usd": 0
}
```

计数和金额的关系如下：

- `successful_requests` 按当前时间、渠道、模型、令牌、搜索和费用筛选范围内的成功 2xx 日志行计数，只包含渠道日志，不按请求 ID 去重；客户端最终请求数仍由请求历史接口统计。
- `estimated_requests`、`zero_requests`、`partial_requests` 和其他未知状态构成成功请求的主状态拆分。`zero_requests` 包含已知零价和本地免费，`local_free_requests` 是其中本地倍率为零的子集。
- `unknown_requests` 包含 `partial_requests`、`historical_requests`，以及 `usage_missing`、`unpriced_model`、`invalid` 等其他未知状态；不要再把细分计数加到未知数上。`historical_requests` 是未知请求中的历史子集。
- 恒等式为 `successful = estimated + zero + unknown`；`unknown = partial + historical + 其他未知`。部分和历史按状态互斥，本地免费包含在零金额计数中。
- `site_pricing_requests`、`local_estimate_requests` 按明确来源统计成功请求；没有明确来源的旧请求仍计入历史/未知，不能猜进站点来源。`mixed_requests` 按计费方式统计。它们与状态计数可以重叠，不能相加当作成功总数。
- `recorded_cost_usd` 是按已保存来源和请求时倍率计算的安全有效记账合计，包含已知的完整、部分和历史金额。`estimated_cost_usd` 只包含完整的 `estimated`、`zero_price` 和 `local_free` 有效金额；`partial_cost_usd` 与 `historical_cost_usd` 单列。
- 未定价、缺用量和非法金额不属于完整估算，也不把缺失金额按零补进 `estimated_cost_usd`。
- `currency` 固定为 `USD`。汇总不使用账户余额币种，也不做汇率换算。

`reconciliation` 当前永远为 `not_reconciled`。这只表示“尚未与上游逐请求账单核对”，不是“已确认少收/多收”，也不是“已确认 0 美元”。当前没有上游账单身份、币种和权限接口，不提供手工确认或自动对账入口。

空范围返回上面完整的零计数结构。数据库读取或聚合失败则返回明确错误，页面显示读取失败；不能把失败变成零汇总，也不能因此显示“没有未知请求”。

控制台页面把汇总金额标为“已记录费用”，并显示类似“完整估算 N/M、K 条未知/部分、尚未与上游账单对账”的覆盖说明。`M` 是成功请求总数，`N` 只包含完整可知的 `estimated` 和零金额状态；未知与部分不能算进完整覆盖。工具卡、趋势图、模型/渠道分布和统计表中的金额都遵循“已记录费用”口径，不称为实际扣费或上游账单。

## 费用筛选

日志、统计和概览共享三个参数：

| 参数 | 可选值 |
| --- | --- |
| `cost_source` | `site_pricing`、`local_estimate` |
| `cost_status` | `estimated`、`zero_price`、`local_free`、`usage_missing`、`unpriced_model`、`partial_estimate`、`invalid`、`historical_unknown`、`not_charged` |
| `cost_basis` | `token`、`per_call`、`mixed`、`unknown` |

费用筛选与时间、模型、渠道、令牌、来源状态、搜索和请求 ID 条件共同生效。历史状态按元数据版本推导；`cost_source` 不是 `site_pricing` 或 `local_estimate` 时不会被猜成站点。旧记录可能没有来源，可通过 `cost_status=historical_unknown` 找到，不能把空来源映射成站点来源。

不支持的来源、状态或计费方式按“无匹配”处理，不能忽略该条件后退回全部记录。`mixed` 是计费方式，不是来源；按来源筛选应使用 `site_pricing` 或 `local_estimate`。

`cost_basis=unknown` 是合法筛选，可以找到计费方式依据缺失的行。旧空/无效来源不匹配 `local_estimate`，其金额仍沿用已保存倍率的本地有效记账规则。筛选 `not_charged` 时，日志可显示失败行，但成功费用汇总为空并显示“暂无成功请求”。

所有日志列表、计数、趋势和费用汇总使用同一参数化表达式，用户输入不会拼接进 SQL。缓存键包含搜索、请求 ID 和三项费用筛选。切换筛选会重置分页；旧请求的迟到响应不能写入新筛选结果。

## 本地记账与软限额

同一次成功请求的日志金额和 Token 结算使用同一次费用解析快照，避免日志显示站点价而结算又按本地价重复计算。快照随转发结果释放，不跨请求缓存。

Token 结算仍是本地记账：

- `token_settlements` 回执保证同一事件重试不重复累计；旧回执和旧用量不会被新费用状态重新计算或迁移。
- 费用限额是请求完成后的软限额。并发请求可能同时通过检查，不能保证精确预留，也不是跨实例共享钱包。
- 金额未知或部分时仍保留成功请求的 Token、次数和已知用量；“未知费用”不等于“没有用量”或“免费”。
- 金额或数量非法时不会输出 `NaN`、`Infinity` 或负数金额；本地回执用 `cost_invalid=true` 和运行指标提示需要核对，不会自动补扣或改写既有回执。

请求日志的费用解释和 Token 累计都是本地口径。上游最终账单可能因缓存、分组、阶梯价、服务层级、退款或供应商币种而不同；当前页面不把任何本地金额称为“已对账”。

余额快照保留 Provider/账号原本的币种。费用汇总和请求估算固定使用 `USD`，系统不按汇率把余额换成 USD，也不会用余额变化推算单请求费用。余额趋势与请求费用只能在各自币种和各自口径内理解。

## 请求日志 JSON 契约

管理员日志和下游令牌日志的安全投影包含以下费用字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `cost_metadata_version` | integer | 新请求为 `1`，旧请求为 `0` |
| `cost_source` | string | `site_pricing`、`local_estimate` 或空/历史值 |
| `cost_status` | string | 上表允许的状态 |
| `cost_basis` | string | `token`、`per_call`、`mixed` 或 `unknown` |
| `effective_cost` | number 或 null | 安全的有效费用；无法确定时为 `—`，不返回非有限数 |
| `cost_details` | object 或 null | `model_cost_usd`、`tool_cost_usd`、`currency` 和可选的已冻结 `breakdown` 安全数值 |

`cost_detail_json` 只用于数据库持久化，不直接输出原始 JSON。公开接口只投影经过允许列表过滤的安全数值，不返回账户信息、价格表、凭据、数据库错误或隐藏渠道路由。兼容字段 `cost_breakdown` 只展示请求时确实冻结且适用的 Token 明细，不能用当前价格补造。

费用字段不会改变原有 `cost` 的有效金额规则，也不会修改价格目录数值或转换核心。`site_pricing` 仍不乘本地倍率；本地工具费按现有规则叠加；按 Token、按次、缓存、tier 和 service tier 的数值计算继续兼容，但历史明细只读快照。

## 迁移与读取失败

SQLite、MySQL 和 PostgreSQL 的升级路径只为日志表增加四个带默认值的列：

```text
cost_metadata_version INTEGER NOT NULL DEFAULT 0
cost_status VARCHAR(32) NOT NULL DEFAULT ''
cost_basis VARCHAR(16) NOT NULL DEFAULT ''
cost_detail_json TEXT NOT NULL DEFAULT ''
```

迁移不重写旧金额、不补算旧状态、不删除旧行，也不改写结算回执。普通存储和混合存储的复制、读取和重新打开必须保留这四个字段；旧行的版本 `0` 继续按 `historical_unknown` 解释。

汇总查询读取失败时，API 返回明确错误，页面显示“费用依据未提供”或读取失败状态。空结果才返回全零结构；读取异常不能伪装成零费用。旧后端没有 `cost_summary` 时也不推断覆盖率。

## 页面口径

- **请求日志**：每行显示金额、费用来源、状态和计费方式；未知金额显示 `—`，失败显示未按成功请求记账。
- **概览与统计**：显示已记录费用及完整估算覆盖，注明尚未与上游账单对账。数据面板保留一处范围内总额，详细依据按需展开；渠道和模型分布是同一总额的两种拆分，不能互相相加。较小分组归入「其他」，保留完整合计。
- **令牌页面**：展示令牌自身的累计费用和软限额，取消全实例代理日志费用区。累计费用是本地记账，不能因为累计为零就推断上游免费。
- **账户与余额**：按原币种分别绘制每日余额净变化曲线，零轴居中，增加为正、减少为负。默认每天北京时间 `00:05` 读取启用且支持余额的账号；可在自动任务设置中启停或修改时间，修改后重启生效。固定采样与普通手动刷新分开保存，登记过的账号当天不再重复采集；调度只在固定时间后的 15 分钟内执行，采集失败或中断保持未知，不用较晚读数补造按时记录。只有相邻两天、完全相同账号集合且采集全部成功才比较，首日仅建立基线；账号增减、币种变化、未知余额和缺失日期不补零，曲线不跨缺口。日期是北京时间的采样自然日，例如 `11/24 00:05` 比较 `11/23 00:05`。默认“今日”请求视图同时显示最近 14 天余额变化，其他范围保留该范围内最多 14 天。曲线经过真实日差额，不制造超出相邻值的波峰；充值与消费会相抵，净减少不等于真实账单消耗，不能作为逐请求费用凭证，也不通过汇率换算成请求费用。旧的末次刷新快照保留原值，不冒充固定采样。
- **请求历史**：完整请求与尝试历史用于路由和协议定位，不是费用账单；费用依据以普通日志的请求时快照为准。

不支持余额查询的账号凭据（例如仅提供 API Key 的部分站点）保留采集结果，但不加入余额比较范围；普通超时、认证失败或读取失败仍保留为缺口，不能当作“不支持”排除。每日采样只更新账号的余额观察字段，保留账号开关、名称和自动任务设置；迟到的观察不会覆盖较新的余额。

采样截止时间同时约束凭据准备、上游预算等待和余额读取；超过窗口返回的成功响应也记为未知差额，不保存为有效余额。窗口跨过午夜时仍归属于原定采样日，例如 `23:55` 的窗口延续至次日 `00:10` 之前。排队期间修改了站点平台，执行时会按最新平台选择余额查询方式。

来源、状态和计费方式都以文字显示，颜色只作为辅助提示；筛选或展开状态不会改变金额口径。

## 本机验证边界

本机验证的范围不包括真实 MySQL/PostgreSQL、race detector、真实上游账单接口或生产部署；代码级检查和合成日志、SQLite 迁移、局部聚合数据也不能证明某个供应商的实际扣费。

任何金额页面都应保留“估算”“已记录”“未对账”的限定。需要用上游账单核对时，应在系统之外按供应商账单和币种另行核对；PivotFlow 当前不提供手工账单确认入口。
