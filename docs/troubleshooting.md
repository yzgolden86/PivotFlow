# 故障排查

## 登录页打不开

先访问 `/health`。如果健康检查失败，查看进程日志和端口占用；如果健康检查成功但页面空白，确认二进制包含最新 `web/console` 资源并清理浏览器缓存。

## `credential_locked`

检查数据目录可写、主密钥文件存在且当前用户可读，确认 `FUSION_MASTER_KEY` 没有被错误换行或截断。数据库和主密钥必须来自同一份备份。

## `site_name_exists` 或删除后仍提示重名

确认请求使用的是当前服务实例和数据库。重启旧进程、确认 `SQLITE_PATH`，再在站点列表刷新。不要同时启动两个进程写同一个 SQLite 文件。

## `expired` / `request_failed`

重新验证上游访问令牌或会话 Cookie；Cookie 类型通常还需要数字用户 ID。New API 的系统访问令牌不是所有 Provider 的签到令牌，不能跨平台套用。

## Sub2API 签到不支持

这是当前适配器的明确能力边界，不是缓存问题。Sub2API 仍可刷新余额、同步模型和获取公告；签到需要上游提供兼容端点后再增加适配器。

## `routing_api_key_unavailable`

站点管理凭证有效不等于账号拥有模型路由 Key。请在上游创建启用的模型 API Key，确认它能列出模型，再执行同步站点渠道。

## 渠道同步部分成功

打开渠道同步结果，查看每个账号的绑定状态和最后同步错误。常见原因是账号未同步模型、没有可用 Key、凭证过期、渠道冲突或上游只开放了管理接口。

## 模型测试被拒绝但余额正常

余额接口和模型调用接口可能使用不同权限、Key 或模型映射。先用账号直测确认上游模型，再检查渠道模型映射、协议模式、URL 协议声明、Key 冷却和访问令牌模型限制。

## 请求持续失败或卡顿

按顺序检查：渠道是否启用、模型是否被冷却、Key 是否全部冷却、URL 是否可达、上游是否限流、请求是否触发成本/并发限制。查看请求日志中的状态码、实际模型、Key 索引和冷却原因。不要先关闭所有冷却规则。

单个请求耗时接近 `non_stream_timeout`（默认 120 秒）时，往往不是换渠道慢，而是某个渠道接受了连接却长时间不返回首字节。请求日志里这类记录的耗时会贴近超时阈值，最终以 504 或客户端取消的 499 收尾。把对应协议的首字超时（如 `anthropic_first_byte_timeout`）调低到 20–30 秒，卡住的渠道就会较早判失败、进入冷却并退出候选池，请求继续走下一个渠道。

## 少数渠道分不到流量

先确认它们真的处于同一优先级层：均衡轮询只在**相同优先级**内轮询，低优先级渠道只有在高优先级全部不可用时才会被选中。同优先级内的份额与有效 Key 数成正比，Key 数不同则份额本就不同。

用系统访问令牌调 `GET /system-api/channels/:id/route-diagnostics?model=...` 最直接：它会给出每个渠道的排除原因、有效优先级、模型是否匹配、可用 Key 数和理论流量份额，且不会推进轮询状态。如果启用了粘性轮询，流量集中到少数渠道是预期行为，不是故障。

## 统一映射配了却没生效

三件事按顺序确认：改完是否已重启（映射在启动时读入内存）；映射是否处于启用状态；上游名称是否**逐字**写对。上游名称是精确匹配的，`GLM-5.2` 和 `glm-5.2` 属于两个不同的路由键，只写其中一个不会自动兼容另一个。用“从渠道挑选”从实际清单里选，可以避免手打出错。

## 更改凭证时看不到已保存的内容

这是预期行为。已保存的凭证经加密存储且从不回传浏览器，所以输入框初值为空，显示切换按钮也只会照出空框——因此该按钮只在你输入了内容时才出现，用于核对刚粘贴的长令牌。留空保存表示保持原凭证不变；填入内容则整体替换。
