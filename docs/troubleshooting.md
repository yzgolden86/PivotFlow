# 故障排查

## 登录页打不开

先访问 `/health`。如果健康检查失败，查看进程日志和端口占用；如果健康检查成功但页面空白，确认二进制包含最新 `web/console` 资源并清理浏览器缓存。

## `credential_locked`

检查数据目录可写、主密钥文件存在且当前用户可读，确认 `FUSION_MASTER_KEY` 没有被错误换行或截断。数据库和主密钥必须来自同一份备份。

## `site_name_exists` 或删除后仍提示重名

确认请求使用的是当前服务实例和数据库。重启旧进程、确认 `SQLITE_PATH`，再在站点列表刷新。不要同时启动两个进程写同一个 SQLite 文件。

## `expired` / `request_failed`

重新验证上游访问令牌或会话 Cookie；Cookie 类型通常还需要数字用户 ID。New API 的系统访问令牌不是所有 Provider 的签到令牌，不能跨平台套用。

## Sub2API 签到不支持

这是当前适配器的明确能力边界，不是缓存问题。Sub2API 仍可刷新余额、同步模型和获取公告；签到需要上游提供兼容端点后再增加适配器。

## `routing_api_key_unavailable`

站点管理凭证有效不等于账号拥有模型路由 Key。请在上游创建启用的模型 API Key，确认它能列出模型，再执行同步站点渠道。

## 渠道同步部分成功

打开渠道同步结果，查看每个账号的绑定状态和最后同步错误。常见原因是账号未同步模型、没有可用 Key、凭证过期、渠道冲突或上游只开放了管理接口。

## 模型测试被拒绝但余额正常

余额接口和模型调用接口可能使用不同权限、Key 或模型映射。先用账号直测确认上游模型，再检查渠道模型映射、协议模式、URL 协议声明、Key 冷却和访问令牌模型限制。

## 请求持续失败或卡顿

按顺序检查：渠道是否启用、模型是否被冷却、Key 是否全部冷却、URL 是否可达、上游是否限流、请求是否触发成本/并发限制。查看请求日志中的状态码、实际模型、Key 索引和冷却原因。不要先关闭所有冷却规则。
