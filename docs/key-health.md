# 渠道 Key 健康管理

一个渠道配置了多个 API Key 时，可在「渠道分发」点击该渠道的 **N Keys · 健康管理**，逐个查看脱敏 Key、备注、最近检测时间和异常原因。OAuth 渠道不提供此入口，其凭证由 OAuth 流程管理。

## 状态从哪里来

正常代理请求、渠道测试和现有定时检测会记录实际使用的 Key 的结果。未被使用或检测的 Key 保持「未检测」，不能据此判断它可用或失效。升级前的旧请求日志不会自动回填状态。

这是**最近一次请求的观察结果**，不是永久结论，也不是余额查询：

| 状态 | 含义与处理建议 |
| --- | --- |
| 未检测 | 尚无记录，可以手动复检或等待实际调用 |
| 正常 | 最近一次请求成功，不保证其他模型也能用或余额充足 |
| 认证失败 | 上游返回认证错误，可能无效、过期或被撤销，核对凭证后复检 |
| 额度不足 | 上游明确提示余额或配额不足，到服务商确认额度与恢复时间 |
| 请求限流 | 暂时达到速率限制，稍后重试；不表示 Key 失效 |
| 访问受限 | 可能是模型权限、IP 限制或站点防护，先排查权限 |
| 请求异常 | 可能是网络、模型或服务异常，不能仅凭此状态删除 Key |

不同服务商使用的状态码不同，例如 HTTP 429 既可能是限流，也可能带有明确的余额不足错误。因此页面结合错误内容分类，不只根据状态码判断。PivotFlow 自身的 RPM/并发限制及客户端取消不会覆盖 Key 的健康状态。

## 怎样复检

1. 点击「需关注」筛出异常 Key；也可以查看全部、未检测或已停用的 Key。
2. 选择该渠道已启用的复检模型和请求协议，优先选择你实际会使用的组合。
3. 点击单个 Key 的「复检」，或点击「复检当前筛选」。批量复检仅包含筛选结果中的启用 Key，按列表顺序取前 20 个，逐个执行；检查大量新 Key 时，可在「未检测」筛选下逐批复检，已有结果的 Key 会移出该筛选。其余 Key 也可单独复检。
4. 根据新的检测结果决定是否停用、补充额度、修正配置或删除。

复检会向上游发送真实模型请求，内容为 `Reply only OK.`，输出上限为 64 tokens，可能产生费用。多个 Key 的批量复检会先确认费用；没有启用模型时，需要先编辑渠道添加模型。

「停止后续」会等待当前请求结束，不再启动下一项。关闭面板会中止浏览器请求并停止后续任务，但已经到达上游的调用仍可能产生费用。已停用的 Key 可单独复检，**复检不会自动启用它**。

没有新增自动遍历全部 Key 的定时任务。原有定时渠道检测仍按原来的选择逻辑使用 Key；希望检查所有 Key 时，请主动分批复检。

## 健康、停用与冷却是三回事

- **健康状态**记录最近请求的结果，只提供排查线索，不会自动停用或删除 Key。
- **停用**是手动管理动作，不再参与正常路由；恢复使用需要手动启用。
- **冷却**由原有路由错误处理机制管理。冷却到期不代表 Key 已经恢复，健康状态会保留到下一次有效观察。

例如，一个 Key 可以同时显示「认证失败」和「已停用」；补充额度或修复凭证后，需要重新测试，不能只清除冷却就假定它正常。

## 清理与保存

建议先停用可疑 Key，观察其他 Key 是否能正常承担请求，再决定删除。删除有二次确认；删除最后一个 Key 后，该渠道将无法使用静态 Key 路由。删除没有撤销入口，需要自行保存凭证，必要时重新添加。

检测记录存储在数据库中，重启不会清空。编辑渠道、重排 Key 时，未更换的实际 Key 保留健康状态与停用标记；替换为新 Key 则从未检测开始。若其他页面已修改 Key 列表，操作可能提示「Key 列表已变化」，刷新后核对目标再操作。

健康面板及专用查询接口只返回脱敏 Key，异常原因采用固定安全提示，不展示上游可能回显的完整凭证或请求内容。Key 备注仍来自渠道配置，需要修改时在渠道编辑中操作。
