# 站点与账号管理

## 添加站点

填写名称、基础 URL、平台类型和时区。平台可以手动选择，也可以保存后点击探测。若勾选“添加首个账号”，系统在同一请求中创建站点和账号，避免先创建站点再依赖前端缓存重新检索。

凭证类型按 Provider 能力显示：

- New API 系、AnyRouter、Veloera：用户名密码、访问令牌、Cookie、API Key。
- Sub2API：访问令牌、Refresh Token、API Key。访问令牌为 JWT 时会自动识别 `exp`；同时保存 Refresh Token 后，系统会在到期前自动续期并保存轮换后的令牌。
- OpenAI Compatible：仅 API Key，用于 `/v1/models` 模型发现和路由同步。

自动探测会先尝试 Sub2API、Veloera、AnyRouter、New API 系等管理型 Provider，均不匹配时才使用 OpenAI Compatible。平台探测只识别接口特征，不会凭空生成站点令牌。你仍需提供自己有权使用的凭证。

## 凭证和验证

添加或修改账号后，使用“验证凭证”检查用户信息、余额、模型数量和路由 Key 可用性。验证是一次性请求，不会替换数据库中的凭证；“保存凭证”才会加密写入。

如果提示 `credential_locked`，检查 `FUSION_MASTER_KEY`、`FUSION_MASTER_KEY_FILE` 和数据目录权限。如果提示 `expired`，重新填写上游访问令牌或会话 Cookie，并同时填写 Provider 要求的用户 ID。JWT 的 `exp` 会自动识别；opaque token 没有可解析的 `exp` 时，可在账号凭证表单中手动填写过期时间。Refresh Token 只在对应 Provider 实现续期接口时生效。

AnyRouter 的会话 Cookie 需要用户 ID；Veloera 的 Cookie/令牌可能需要兼容用户头。Sub2API 的访问令牌通常是 JWT，`session cookie` 不是把 JWT 随便填进 Cookie 字段。

### 从浏览器资料导入或修复

站点页、账号页和“更新凭证”窗口提供[浏览器导入](browser-import.md)。页面助手在同来源上游顶层页面导出本地 JSON，也支持 All API Hub 2.0／3.0／4.0 明文账号备份。先检查原文件、明确目标并确认来源，再选择只读验证或停用保存预览；确认应用时使用同一冻结快照。

新账号默认停用、自动维护关闭。修复既有账号只替换凭证并把当前状态重置为未知，保留开关、余额、历史、模型、绑定和渠道。导入验证不自动刷新长期令牌、揭示路由 Key、签到或同步渠道；后续由用户在账号页和渠道差异预览中明确操作。应用响应未知时先读原预览并核对实际账号。

## 余额、签到和变化

“刷新余额”调用 Provider 的账户信息接口并写入当前余额。“签到”先保存签到前余额，再执行 Provider 签到，最后刷新余额；结果会记录奖励文本、签到状态、余额前后值和余额变化。

每次成功读取到余额都会写入“账号本地日期 + 币种”的每日快照；同一天多次刷新保留最新值。数据面板的余额趋势按币种汇总这些快照，可用于查看今日、本周或本月的资产变化。该功能从启用后开始积累，升级前的历史余额不会凭空补造。

同站点定时与手动任务串行，重复的在途操作合并到同一个任务 ID；全局最多 4 个执行任务、128 个登记任务。Provider 的实际 HTTP 请求再按 origin 共享单并发、250ms 最小间隔和 429 冷却，价目表也参与预算。因超时而失败的余额/模型刷新保留有界退避，429 不自动重放签到 POST。账号自动刷新的 6 小时到期点继续按账号 ID 加 0–29 分钟错峰。

“站点维护任务”进度区显示逐项结果，可取消、仅重试已确认失败和部分成功项。离开页面后服务器继续运行；轮询中断保留原任务 ID，使用“重新观察”，不能把未知结果当作失败盲目重新签到。完整语义与默认预算见 [站点维护任务与共享限速](site-tasks.md)。

支持服务端签到的 Provider：New API 系、AnyRouter、Veloera。Sub2API 当前返回 `unsupported`，可以继续使用余额、模型和公告功能。OpenAI Compatible 不提供管理接口，因此不支持余额、签到或公告。需要浏览器挑战的站点会返回 `browser_required`，不会伪造成功。

`browser_required` 表示签到接口被浏览器挑战、验证码或上游网页流程挡住，PivotFlow 不会把这种结果伪装成成功。New API 系站点会在此时再读取上游的“今日是否已签到”状态：如果你已经在外部页面完成签到，回到签到中心重试会自动显示“已签到”；如果上游仍未记录签到，状态保持“需浏览器”。签到中心会优先打开站点配置的浏览器辅助签到地址；未配置时，New API 系默认打开 `/console/personal`，Veloera 默认打开 `/app/me`。

站点“基础 URL”始终用于服务端余额、模型、签到和公告请求。“浏览器辅助签到地址”只是人工打开上游页面的快捷入口，不会参与自动签到，也不会替代基础 URL 做接口请求。

### 站点同步渠道的手动接管

站点同步生成的渠道默认随每日账号刷新一起更新 URL、模型和路由 Key。你如果只想从上游引入部分模型，可以先同步一次，再到渠道页裁剪模型列表；这类手动修改会让渠道进入“手动接管”状态，之后的每日自动同步会跳过它，不会把上游全部模型重新带回来。

会触发手动接管的操作包括：手动修改渠道名称、URL、协议模式、模型列表，或在渠道 Key 管理中修改、启停、删除 Key。调整优先级、倍率、限流、冷却和启用状态不会触发接管，仍保留自动同步。

手动接管渠道在渠道列表会显示“手动接管”徽标。重新生成“同步站点渠道”预览时，这类渠道显示为“保留”，确认后仍保持原内容，不会覆盖手动修改。要恢复上游更新，先在渠道页点击“恢复自动同步”把所有权交回站点投影，再重新生成并确认差异预览。

站点同步读取上游各 Key 的模型、协议和分组。完整发现后，确认消失的上游 Key 会让自动管理渠道显示“停用”，确认后停用渠道并保留请求历史；发现不完整时显示“保留”，不会删除或停用无法确认的渠道。手动管理渠道始终保留。多个账号的预览与结果分别显示，应用时每个账号使用独立配置事务；取消、租约、请求预算和“结果待确认”的恢复方式见 [站点维护任务与共享限速](site-tasks.md) 与 [配置导入与渠道同步](config-import.md)。

## 公告

公告中心按站点聚合、去重和记录已读状态。点击刷新会创建后台任务；任务完成后刷新列表。公告源 URL 是上游提供的参考地址，不等于 PivotFlow 的代理地址。

## Webhook

系统设置中配置一个加密保存的 Webhook URL，可选择低余额和签到失败事件，并设置去重冷却时间。先使用“测试 Webhook”验证网络，再启用真实通知。Webhook 发送失败会保留最后错误，不会阻塞余额或签到任务。
