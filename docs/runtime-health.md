# 后台运行健康

管理员可以从首页的「运行健康」摘要、侧栏「统计 → 运行健康」或全局搜索进入 `#/health`。摘要独立于业务概览读取；业务统计加载或失败时，仍可查看后台运行状态。

页面展示真实后台操作的最近结果与进程累计计数。它不主动探测数据库或上游，也不执行清理、重试或修复；请求成功率继续在[请求日志](request-history.md)中按完整请求和上游尝试分别阅读。

## 先看哪些信息

| 分区 | 关注的问题 |
| --- | --- |
| 费用与请求记录 | 新请求是否暂停准入、费用是否已持久保存、待结算是否积压、请求历史是否能写入 |
| 写入与同步 | 上游日志与失败统计是否写入、主库复制是否失败或丢弃、本地副本是否需要核对 |
| 维护与恢复 | 日志保留策略、最近清理、下一次计划、启动时配置和历史恢复的实际结果 |
| WebSocket 资源 | 下游连接、执行会话、上游连接、会话上下文预算与历史拒绝计数 |

每张卡片先显示状态与原因，再显示当前积压和累计记录。「最近处理与累计记录」可用鼠标或键盘展开，查看最近尝试、成功、失败、失败后再次成功和取消次数。卡片入口分别连接完整请求、上游日志、令牌用量和保留设置。

## 状态的含义

| 状态 | 含义 |
| --- | --- |
| 暂停准入 | 待结算文件不可用，或进程正在关停；新的代理工作不能继续准入 |
| 当前异常 | 最近本地写入或结算存在未恢复失败，或者仍有结算事件只在内存中 |
| 需要关注 | 等待队列压力、近期丢弃、结算积压、复制或清理失败、启动历史恢复不完整，或副本差异仍需核对 |
| 状态未知 | 指标能力缺失、数据版本不兼容、读取失败或快照已过期 |
| 正在处理 | 已接收的后台任务仍在处理或等待结算 |
| 正常 | 已观测到成功，当前没有这项操作的未恢复失败 |
| 尚无操作 | 已启用，但尚未观测到处理；WebSocket 则表示当前没有会话或连接 |
| 未启用 | 已确认当前配置或存储模式不需要这项服务 |

整体状态按「暂停准入 → 当前异常 → 需要关注 → 状态未知 → 正在处理 → 正常 → 尚无操作」取最高优先级；未启用组件不提高整体等级。缺少可选存储指标时，复制、缓存同步与启动恢复显示未知。

当前提示阈值是：队列或 WebSocket 预算使用量至少 **80%**；最近 **60 秒**内发生丢弃；最老待结算事件等待超过 **30 秒**。历史累计失败、丢弃、WebSocket 拒绝和重连独立保留，后续成功不会把这些计数清零。

纯关停取消单独计数。若一个组合错误同时包含取消与磁盘、SQL 或超时故障，真实故障仍记录为失败并写入服务端日志。

## 刷新与快照

- 自动刷新在上次读取结束后等待 **10 秒**，同一页面最多保留一个读取请求。
- 单次读取 **8 秒**超时；浏览器页面隐藏时停止调度，恢复可见时自动更新。
- 取消自动刷新会停止调度并取消该页正在读取的请求；「刷新」仍可手动读取。
- 成功快照超过 **30 秒**，或下一次读取失败时，当前状态变为未知。页面保留上次计数和结果供排查，组件状态标记一并变为未知。
- 暂停后尚未过期的快照明确显示「上次快照」。重新读取成功后才恢复当前状态判断。

时间按浏览器时区显示。累计计数以本次进程为单位，重启后清零；持久待结算积压会从待结算文件重新读取。

## 计数与恢复边界

`queued` 表示等待通道中的记录，`buffered` 包含工作线程已取出、正在凑批或正在写入的记录。通道为空时，批次仍可能尚未写完。`written` 表示存储调用成功处理的记录数，不代表去重后的数据库总行数；操作失败次数与最终未保存的记录数也使用不同单位。

混合存储先保存本地日志和请求历史，再尽力复制到主库。请求历史复制按批次计数，等待量包含正在执行的批次，独立容量为 64 个批次，单批最多 32 条请求。日志复制卡片的等待量来自共享队列，可能包含两类任务；日志失败、丢弃和执行数则只指日志任务。

复制失败或丢弃的批次不会自动补发。「失败后再次成功」说明后来的操作已能执行，不能证明此前缺失的主库记录已补齐。仅备份主库可能遗漏尚未复制的本地记录，备份边界见[请求历史](request-history.md)与[安全与备份](security.md)。

副本同步失败会保留 `cache_may_be_stale` 提示。一次无关写入成功无法验证此前全部差异；修复数据库、磁盘和权限后，按[部署](deployment.md)与备份流程恢复并核对副本。

启动恢复分别显示配置副本、上游日志历史和完整请求历史的结果。配置恢复成功后，某项可选历史恢复失败仍会单独显示；关闭历史恢复与恢复失败使用不同状态。普通日志和请求历史共用保留期限，调试日志使用独立清理周期；调试关闭并成功清空后不再调度该清理循环。

## 出现异常时

1. 「暂停准入」或「仅在内存」大于零时，优先恢复待结算文件所在的持久卷、磁盘空间与写入权限；确认内存事件已保存后再安排正常关闭。结算细节见[可靠结算与流式恢复](reliability.md)。
2. 主库结算失败时，已持久保存的事件继续幂等重试。观察待确认数量和最老等待时间，并结合服务端错误日志检查主库与副本。
3. 写入、复制或清理失败时，核对最近失败时间及累计损失，检查数据库连接、磁盘和保留配置；读取健康页不会触发额外任务。
4. 成功恢复后继续核对历史损失和副本差异。当前成功与历史完整性是两个独立事实。

## 复制脱敏诊断

「复制脱敏诊断」使用显式字段允许列表，只包含受控组件状态、计数、存储类别、时间和固定错误类别，不包含凭据、Token 哈希、结算事件、数据库路径、DSN 或错误原文。后端新增的额外字段也不会被直接复制。

诊断带 `schema_version`、`snapshot_status` 和 `received_at`。过期诊断保留原始观察结果，并标为 `stale`；阅读者应先判断快照状态，再解释里面的组件结果与计数。浏览器剪贴板不可用时尝试兼容复制，并恢复原控件焦点。

## 只读接口与兼容

`GET /admin/runtime-metrics` 继续要求管理员会话。原有 `billing`、`request_traces`、`token_failure_stats` 和 `responses_websocket` 字段保留，新增 `started_at`、`observed_at`、`logs`、`cleanup`、`storage` 与 `health.version=1`。

当前源码还提供可选 `request_cache`，包含[请求缓存](request-cache.md)的当前进程策略、正文容量及固定原因计数；它不改变整体健康等级。读取不会触发过期清理或上游请求。脱敏诊断先校验缓存版本、容量、时间和原因字段，再复制结构化观察；旧后端省略或返回 null 时保持未提供状态，不补成已启用或零容量。

接口只复制内存观察，不读取数据库来判定健康。错误类别限定为 `timeout`、`operation_failed` 或空值；存储类别限定为 SQLite、MySQL、PostgreSQL、混合存储或未知。Token 自助页面不开放这项实例运行指标。

前端需要新版健康结构。旧后端缺接口或缺 `health` 时明确提示更新；缺字段、无效计数、不可表示的时间和不兼容版本不会被补成零或正常状态。升级时应同步构建并部署后端与控制台资源。
