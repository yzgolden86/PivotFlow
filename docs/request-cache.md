# 可选请求缓存

请求缓存用于短时间内重复发送完全相同的文本请求。它默认关闭；管理员启用后，客户端还需通过 `X-PivotFlow-Cache` 明确选择使用。响应只保存在当前网关进程的内存中，重启后清空。

它适合重复的无工具文本查询。上游 prompt cache、网关响应缓存、模型目录缓存及 WebSocket 会话复用各有自己的语义和计数。

## 启用与使用

在「系统设置 → 运行配置 → 请求缓存」中启用并保存。五项缓存设置都需要重启生效，沿用[系统设置](configuration.md)的优雅重启流程。面板里的「当前进程策略」来自运行中的实例，与尚未保存的草稿分开。

| 客户端请求头 | 行为 |
| --- | --- |
| `X-PivotFlow-Cache: use` | 查找可复用响应；未命中时正常调用上游，安全完整的结果才保存 |
| `X-PivotFlow-Cache: refresh` | 开始时移除该精确请求的旧条目，重新调用上游；失败后也不继续复用旧条目 |
| `X-PivotFlow-Cache: bypass` | 本次不读取、不保存缓存 |
| 未发送或模式无效 | 本次绕过缓存 |

请求中的 `Cache-Control: no-store` 禁止读写。已选择 `use` 或 `refresh` 的请求遇到 `Cache-Control: no-cache` 或 `Pragma: no-cache` 时强制刷新。`X-PivotFlow-Cache` 由网关消费，不传给上游。

下面的命令需要自行设置网关地址和下游访问令牌，并选择令牌清单中可调用的模型。两次请求应保持正文和语义请求头相同：

```bash
curl -i "$PIVOTFLOW_BASE_URL/v1/chat/completions" \
  -H "Authorization: Bearer $PIVOTFLOW_API_TOKEN" \
  -H "Content-Type: application/json" \
  -H "X-PivotFlow-Cache: use" \
  -d '{"model":"deepseek-v4.1-flash","temperature":0,"messages":[{"role":"user","content":"用一句话说明什么是 API 网关。"}]}'
```

响应中的 `X-PivotFlow-Cache` 为 `hit`、`miss`、`refresh` 或 `bypass`。缓存关闭且客户端未发送缓存头时，不额外添加这项标记。每次请求仍有新的 `X-PivotFlow-Request-Id`，可进入[完整请求历史](request-history.md)查看原因。

## 哪些请求可以复用

首期支持 `POST /v1/chat/completions` 和 `POST /v1/messages`，要求 JSON、非流式、显式 `temperature=0`、一个候选，以及只包含字符串或纯文本块的消息。Anthropic 请求还需合法的 `max_tokens`。

请求字段采用递归白名单。工具定义、工具调用和结果、函数、图片或音频、思考与会话状态、未知字段、会话／线程／幂等请求头、查询参数和编码请求体都会绕过。Responses、Gemini、WebSocket 和流式请求继续按正常代理路径处理。`temperature=0` 表达客户端接受短期复用的选择，不保证模型服务会永远生成相同内容。

实际转发若发生协议转换、语义正文改写、OAuth、AnyRouter 兼容处理或自定义请求规则，也不保存响应。纯模型名称重定向可以使用缓存；映射修改会使旧条目失效。

只保存 HTTP 200、完整 JSON 和受支持的文本终态。错误、被截断的结果、工具输出、不可识别字段、非 JSON、写出失败、客户端取消，以及上游 `no-store`／`no-cache`、`Vary: *`、Cookie 或仍带编码的最终响应都不保存。未保存缓存不会阻止原本合法的代理请求完成。

## 身份、模型与费用

缓存按下游令牌 ID 和哈希、客户端协议、路径、原始正文及语义请求头精确隔离。不同令牌不能共用响应；正文的空白、字段顺序、模型别名或请求头变化都可能形成不同条目。统一模型清单和模型权限仍沿用[模型路由](model-routes.md)，缓存不会改变令牌获取到的模型清单。

每次请求仍经过身份、模型／协议／渠道权限、令牌和全局并发、费用限额预检以及可靠结算准入。缓存来源渠道必须仍属于允许的候选。命中不选择上游凭据，不占上游并发或 RPM，不推进路由轮询游标，也不添加伪造渠道健康日志。

缓存命中只有在完整写出后才记一次客户端成功请求，新上游 tokens 和费用为零，复用已有幂等结算路径。写出失败或取消不会记成功。命中历史的真实上游尝试数为零；请求历史与上游日志采用各自的统计口径。

缓存 JSON 原样保留此前的 completion／message ID 和 `usage`，不会伪造一份零 token 的模型响应。下游 SDK 如果直接累计每份 JSON 的 `usage`，仍可能重复计算；应结合 `X-PivotFlow-Cache: hit` 区分复用响应。网关只复用 JSON 和 Content-Type，不重放此前的网关请求 ID、上游限额、Cookie、日期等瞬态头。费用说明见[本地记账与上游对账边界](cost-semantics.md)。

## 容量、过期与清空

| 系统设置 | 默认值 | 允许范围 |
| --- | --- | --- |
| `request_cache_enabled` | `false` | `true`／`false` |
| `request_cache_ttl_seconds` | 60 秒 | 5–3600 秒 |
| `request_cache_max_entries` | 256 条 | 1–4096 条 |
| `request_cache_max_bytes` | 32 MiB | 1–128 MiB |
| `request_cache_max_entry_bytes` | 1 MiB | 4 KiB–1 MiB |

过期条目不再复用；正常缓存流量会清理过期内容，容量满时按最近最少使用顺序淘汰。读取观察面板不会清理条目，因此「驻留条目」可暂时包含已过期条目，面板会单独显示数量。

已保存响应正文和在途捕获正文各自受总容量限制；单条响应也有上限。最多登记 4096 个活跃精确请求键，结束后释放。超过预算时继续正常转发，只放弃这次缓存。容量显示按正文 payload 计算，不能当成整个 Go 进程的堆内存上限。

渠道、Key、统一模型映射或令牌权限修改会清空旧缓存。手动「清空缓存」还会使之前在途请求的旧填充失效，防止清空后重新写入旧结果。同一精确请求的较晚刷新也会阻止更早的慢请求覆盖新结果。这些操作不会取消已发出的上游请求。

手动清空保留当前进程的累计计数。清空超时意味着结果暂时未知；界面不会自动重复 DELETE，可重新读取观察确认。全部缓存状态与累计计数在进程重启时清零，多实例分别保留自己的缓存。

## 观察与排障

| 管理接口 | 内容 |
| --- | --- |
| `GET /admin/request-cache` | version 1 的当前进程策略、时间、驻留／捕获容量和固定原因计数；只读 |
| `DELETE /admin/request-cache` | 清空响应、使旧填充失效，返回当前观察；需要管理员确认操作 |
| `GET /admin/runtime-metrics` 的可选 `request_cache` | 同一份只读观察，供[运行健康与脱敏诊断](runtime-health.md)使用 |

这些接口要求管理员身份，API Token 自助会话不能读取实例级观察或清空缓存。接口、复制诊断和历史原因不包含请求／响应正文、缓存键、凭据或来源请求 ID。原因统计是稀疏映射：未出现的固定代码表示尚无该类事件，整个字段缺失则视为不完整数据。

「命中」统计完整写出成功的复用响应；「查找」表示实际复用查找，刷新和绕过单列。拒绝保存、失效和过期属于事件计数，同一请求可能产生多项事件，不能相加作为客户端调用总数。

请求没有命中时，先查看完整请求的缓存原因，再确认当前进程已启用、请求有 `use`、正文和请求头相同、字段受支持、条目未过期，以及来源渠道和权限未发生变化。缓存失败不会改变可靠结算、模型权限或既有故障切换规则。

本地合成验收与环境边界见[阶段验证记录](superpowers/plans/2026-11-23-request-cache-verification.md)。
