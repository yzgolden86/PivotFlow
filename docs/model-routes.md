# 模型路由与统一模型清单

控制台「模型路由」从一个客户端请求名出发，查看当前统一组、相关渠道、路由策略和尝试限制，并进入该请求模型的历史。入口为 `#/routing`；渠道诊断也提供相同范围的工作台链接。

## 模型列表和统一映射

在系统设置 → 路由策略保存启用的统一映射后，客户端模型列表立即按统一名称归并。映射组内任何启用成员出现，列表就显示一次统一名称。新建令牌的模型权限留空表示不限制；列表仍受该令牌的协议和渠道范围约束。

例如将 `DeepSeek-V4.1-Flash`、`deepseek-ai/DeepSeek-V4.1-Flash`、带渠道前缀、`-1017`、`-free` 和其他已配置变种映射到 `deepseek-v4.1-flash` 后，`/v1/models` 返回一个 `deepseek-v4.1-flash`。Gemini 列表对应 `models/deepseek-v4.1-flash`。上游精确拼写继续保留，转发时使用渠道实际配置的模型名。

令牌编辑器使用当前启用渠道的统一模型清单，每页最多 50 项，检索覆盖全部当前别名。「全选本页模型」只添加本页；未选模型表示不限。旧令牌已有的别名权限保留，可以在「本页之外的原有选择」中查看和移除，避免编辑其他字段时改写权限。

白名单按当前统一组求值：填写统一名称或组内任一别名，允许该组。停用映射后恢复按原名校验。模型可见表示配置和权限覆盖；Key、协议能力、时段、冷却和容量仍需在实际请求中检查。

## 上游模型消失后的处理

站点模型与路由的完整成功同步会替换旧模型快照、更新自动投影渠道。上游成功返回有效空模型数组时，也会清空该自动渠道的模型并停用；完整发现确认移除或停用的 Key 对应渠道同样清空路由模型并停用。渠道、请求日志和历史仍保留；上游恢复供应后可重新同步，恢复时尊重用户保存的启停选择。重新启用站点不会恢复上游已移除的供应。手动接管的渠道继续保留人工配置。渠道模型刷新选择 `replace` 时，也会移除不再返回的模型；`merge` 只添加。

模型响应中的分页信息表明还有后续结果、总数与当前清单不一致，或返回无效结构时，本次发现不会作为完整模型快照覆盖现有供应；同步显示未完成或失败，保留原模型与映射，待上游返回完整结果后再协调。

成功同步确认移除的上游名称，在所有剩余渠道均不再配置时，会自动从统一映射成员中清理。比较保留精确拼写；其他渠道仍存在、渠道或模型只是停用、手动渠道仍配置的名称都会保留。未被本次同步观察过的手填成员也保留。清理按设置原值做条件更新，遇到并发设置修改后重新读取，避免覆盖用户编辑。

已启用且未过期令牌的旧白名单仍引用某个别名时，保留该别名的映射关系，以保持该令牌对统一组的已有权限；它不会单独出现在统一模型清单中。管理员可先把旧白名单改成统一名称，再手动移除保留的别名。自动清理不改写令牌权限。停用或过期令牌不属于此保留范围，重新启用前应核对白名单。

局部发现、请求失败、返回含义不明确的空清单会保留旧证据，等待后续成功同步。读取模型列表、路由工作台和历史本身不会同步上游或修改映射。

映射清理遇到持续并发编辑、快照读取或保存失败时，站点任务会显示未完全完成；消失名称作为过期事实保留，下一次完整成功同步可继续清理。更新后的自动渠道已经反映当前模型，过期事实不作为启用路由。渠道 `replace` 的模型保存与映射清理在同一事务中完成，已知清理失败会回滚，便于重试；主库已提交但副本失败、提交结果待确认分别显示。

当一个组不再有任何启用成员时，客户端列表和模型路由左侧清单均不再展示该统一名称。组配置仍可在系统设置编辑；直接输入模型名进行诊断时，可以查看停用渠道等排除原因。上游变化在成功同步后反映到本地清单；网关不会仅凭某次调用失败判定模型已永久移除。

## 查看当前路由

1. 从左侧选择统一模型，或输入完整原始请求名。
2. 选择客户端协议和观察令牌。全局管理员观察不套用某个令牌的准入限制；指定令牌时使用当前生效的模型、协议、渠道、费用和并发观察。
3. 阅读相关渠道的候选层和尝试状态。停用、被排除或通配兜底的相关配置也会列出原因。
4. 需要修改时进入对应渠道，或使用「路由设置」「健康设置」入口。查看页面不会发起上游测试。

```mermaid
flowchart LR
  A[令牌准入] --> B[精确和统一组候选]
  B --> C[时段、日额度与冷却]
  C --> D[优先级、健康和均衡]
  D --> E[粘性与令牌渠道限制]
  E --> F[Key、协议 URL、RPM 与并发尝试]
```

「进入候选池」和「当前可尝试」分开显示。没有 Key、Key 不允许原始请求名、协议不兼容或容量已满的渠道，可能进入候选池但在尝试时跳过。OAuth 凭证的可用性需要解密或刷新时，诊断显示待确认。全冷却兜底显示提前试探，表示允许在恢复前尝试。

## 权重、健康、粘性和费用

| 观察 | 应怎样理解 |
| --- | --- |
| 基础 → 有效优先级 | 有效优先级扣除失败与首字惩罚，可能跨越基础层 |
| 轮询权重 | 启用 Key 总数减当前冷却数，最小 1；不等于模型范围内 Key 数 |
| 同层权重参考 | 令牌渠道过滤前的同层参考；低层是故障转移时的条件份额 |
| 健康与首字样本 | 来自整个渠道的近期上游样本，缺样本显示未知 |
| 最近成功渠道 | 粘性是否前移还取决于真实均衡后首位的基础优先级，不能预测下一次必选 |
| 渠道与 Key 倍率 | 本地费用配置，可用 Key 有不同倍率时显示范围 |
| 站点价目缓存 | 只读取已有本地缓存；不证明当前模型有适用价格或费用已对账 |
| 已保存上游尝试 | 本机今日、精确请求模型及协议的历史记录；排除无渠道的最终汇总行 |

工作台使用生效的全局 balanced/sticky 和健康配置，没有单独的每组策略保存表单。映射热生效；路由策略和健康配置仍按进程生效快照解释。价格观察不能作为跨渠道最低成本保证。

快照不会推进渠道、Key 或 URL 游标，不预留并发或 RPM 槽位，不清理过期冷却／粘性，不解密或刷新凭证，不拉取站点价目。实际请求会重新检查动态约束。

## 请求历史与链接

「查看请求历史」按原始请求名、客户端协议和当前令牌范围精确筛选。模型和协议使用字节相等条件，大小写／重音／尾部空白不同的名字不会因数据库排序规则混合。历史中的模型身份不会随今天的别名关系改变；选择某个别名后，查看的是用该别名发起的请求。

链接保存模型、协议、令牌、时间、结果、搜索和页码，打开详情或浏览器后退均可恢复。无效范围会显示错误，避免悄悄扩大为全部令牌。

当前历史存储的模型身份最多 191 字符。工作台可诊断最多 512 字符的请求名；超过历史边界时提供「普通请求历史」，保留协议与令牌范围，明确无法精确过滤，不截断名称后匹配。旧记录缺少协议或完整请求身份时不推测补齐。

## 管理接口

| 只读接口 | 参数和边界 |
| --- | --- |
| `GET /admin/routing/models` | `search`、`limit`、`offset`；默认 50，最多 100；完整别名搜索，预览最多 8 个别名 |
| `GET /admin/routing/models?enabled_only=true` | 模型路由清单和令牌选择使用的启用模型视图，排除空组、停用模型和通配配置后分页 |
| `GET /admin/routing/diagnostics` | `model` 必填，`client_protocol`，可选正整数 `token_id`，以及分页参数；组名预览最多 50 |
| `GET /admin/channels/:id/route-diagnostics` | 既有渠道诊断，共用同一模型诊断核心 |

两个新接口返回 `version: 1`。模型名和检索最多 512 字符，拒绝控制字符、无效协议和重复参数。指定不存在令牌返回 404；存储失败返回固定错误代码。诊断先对完整相关集合求值再分页，份额与层级不按当前页重算。

响应只包含安全配置与观察：URL 使用索引和协议状态，Key 使用数量与倍率，不包含完整令牌、Key、URL、代理、Header 或请求规则。
