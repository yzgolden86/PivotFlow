# 可信运行第一阶段设计

用户已在 2026-11-19 批准按研究报告顺序推进。本次交付第一组 P0：成功请求结算、认证请求重定向、流式恢复边界。后续请求历史与 UI 接入流程继续按研究路线推进。

## 实现选择

单纯增大队列不能解决数据库故障，直接同步增量写入不能安全重试。本次采用本地 SQLite 待结算记录 + 主库事务去重；沿用现有数据库、Go 和协议实现。该实现选择由维护者根据已批准目标作出。

成功请求完成时立即累加内存软限额，并将不含原始凭据的结算事件写入本地持久记录。事件固定 ID、发生时间、Token 哈希、用量及已解析价格；后台以同一 ID 重试，主库原子完成事件去重和累计统计。确认主库与必要副本一致后删除待处理事件。队列只用于唤醒，队列饱和不能丢结算。失败请求的可丢弃统计保留现有语义。

生产入口启动时打开独立 `billing-pending.db`，默认与配置的 SQLite 数据路径同目录，未配置时为 `data/`；可用 `PIVOTFLOW_BILLING_JOURNAL_PATH` 指定持久文件。开启处理前重放历史事件并重新加载 Token 费用，重放失败则启动失败，避免额度低估。测试通过临时数据库显式启用该路径。独立 journal 不进入用户 JSON 导入导出，也不因日志清理删除；应与数据库作为同一实例的运行数据保管。

运行期 journal 写失败时保留未写事件并尝试落库，公开故障状态，阻止新的代理调用继续扩大未持久费用；已在途请求仍结算。后台恢复后解除限制。无法同时承诺磁盘失效和强制杀进程时数据完整，文档必须清楚说明这一物理边界。主库暂时不可用时，已持久事件可以跨重启恢复。

审阅后增加数据边界：上游负用量写入事件前归零；负数、非有限或超过微美元范围的金额按未知金额零值记录，并持久标记 `cost_invalid`、输出 ERROR 与 `invalid_cost_events` 指标。此类数据异常不进入存储故障的全局阻断循环；journal 与 SQL 本身继续严格校验。金额无效事件保留用量，需人工对账，本阶段不保证其金额准确也不自动补扣。

认证 HTTP 只允许同源重定向：scheme、大小写归一主机名、默认端口归一后端口一致，限制跳数并拒绝 URL userinfo；保留 Provider 原有地址检查。浏览器授权导航和已有拒绝全部跳转的请求不放宽。

流式行为先核对现有契约及测试，针对缺口补回归；客户端取消不重试/不冷却，语义输出后不重放，跨传输恢复及线程隔离沿用现有边界。

## 验收与限制

- 成功队列饱和、暂时 DB 失败、确认结果丢失、重启恢复和关停均有合成测试；重试不重复费用、次数或用量。
- 免费、站点价目及倍率保持当前口径；本次不把软限额改为并发预扣钱包。
- 新表为增量迁移，支持 SQLite/MySQL/Postgres；混合存储不重复叠加已恢复的 Token 统计。
- 运行指标公开待结算数、持久化/落库失败与恢复；只提供聚合数，不返回 Token 哈希或凭据。
- 重定向测试覆盖 301/302/307/308，同源可用，跨源目标不会收到请求。
- 必须 `-tags sonic`，运行后端全套、相关 race 子集、lint 和构建；生产数据和现有可执行文件不用于验证。
