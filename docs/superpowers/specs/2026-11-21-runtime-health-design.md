# P1 运行健康面板设计

状态：沿用户已确认的路线实施。2026-11-21；接续已完成的 P0 可靠结算和 P1 请求历史。

## 目标与依据

让个人部署管理员判断当前是否受到结算、写入、同步或清理故障影响，并知道需要检查什么。运行健康与请求成功率分开：业务上的 429、取消和重试不直接证明后台存储故障。

现有 `/admin/runtime-metrics` 已有结算、失败统计队列、请求历史和 WebSocket 资源计数。缺口是当前失败与历史累计失败无法区分，普通日志最终写入失败缺少计数，普通日志清理忽略返回错误，混合存储的日志同步失败和可选启动恢复失败只有服务端日志。继续使用这些真实工作路径，不另建探测数据库或人工“健康”状态。

依据见 [实施路线](../../research/2026-11-19/recommendations.md)、[可靠结算](../../reliability.md)、[请求历史](../../request-history.md)。参考项目已在上一阶段研究，本阶段不重复抓取。

## 方案选择

| 方案 | 优点 | 代价 | 决定 |
| --- | --- | --- | --- |
| 只把原有累计计数放入首页 | 改动少 | 无法判断是否已恢复，也无法看到清理失败 | 不采用 |
| 扩展真实运行指标，首页摘要加独立详情页 | 故障依据可核验，既方便发现也方便排障 | 需要给后台操作补状态记录 | 采用；这是实施者在已授权路线内的选择 |
| 引入外部监控、告警和主动数据库探测 | 可服务更复杂的部署 | 新依赖与配置，探测可能阻塞管理接口，超出本阶段范围 | 后续按部署需要考虑 |

## 边界

- 保留现有 `/admin/runtime-metrics` 字段与语义，只添加字段。API 继续仅允许管理员会话，不向下游 Token 会话开放。
- 指标读取只读取进程状态，不触发数据库访问、清理、结算、恢复或重试。
- 不改变计费金额、幂等回执、队列预算、历史保留策略、混合存储的一致性或 WebSocket 重放契约。
- 普通日志仍每小时首次执行；调试日志仍启动即检查，按现有两分钟周期和 200 条批次清理。取消时记取消，不假报存储失败。
- 不添加数据库表或环境配置，不安装新前端依赖。使用现有 Go、Gin、React、TypeScript、主题令牌及共享组件。
- 使用 `-tags sonic`、`-buildvcs=false`；主工作区的未提交改动、生产程序、数据、密钥和发现链接均保留。
- 仅在隔离工作区实施，验证后将本阶段差异整合回主目录。未经新的授权不推送、发版、部署或替换运行程序。

## 运行状态记录

新增无业务依赖的 `internal/monitoring` 包。零值可用的 `OperationMonitor.Begin() func(error)` 在实际操作开始与结束时记录：

- `active`、`attempts`、`succeeded`、`failed`、`cancelled`；失败次数是操作次数，不是丢失记录数。
- `failing`、`consecutive_failures`、`last_result`；成功清除当前失败，累计失败保留。
- `last_attempt_at`、`last_finished_at`、`last_success_at`、`last_failure_at`、`recovered_at`，均为 Unix 毫秒，未观测为 0。
- `last_error_code` 仅为 `timeout`、`operation_failed` 或空值；不保留错误原文。取消单独计数，不清除已有未恢复故障。

`recovered_at` 表示一次失败后已有后续操作成功。它不证明丢弃记录已补发，也不证明先前所有副本差异已修复。并发操作以完成时观测到的结果更新状态；闭包重复结束不重复计数。

普通日志和请求历史补 `buffered`，表示已从通道取出、尚未完成处理的记录，包括待凑批和正在写入的批次。`queued` 继续是通道等待数。两者单独显示，避免通道已空却误以为所有记录已落盘。最终失败记录数和累计丢弃记录数单独保存。

队列丢弃补 `last_dropped_at`。队列使用率达到 80% 提示压力；最近 60 秒出现丢弃提示近期损失，过期后仍展示累计数，不能永久按累计数判定当前故障。

结算补 journal 与主库结算操作状态和 `oldest_pending_at`。待确认最老事件超过 30 秒提示积压；无历史结算时显示尚无结算，而不是把 0 时间解释成最近成功。

## 存储与启动恢复

`StorageRuntimeStats()` 是可选只读能力，DTO 位于 `internal/model/runtime_health.go`，避免 `storage` 与 `storage/sql` 循环依赖。

- 纯 SQLStore 只公开驱动类别，不返回 DSN、路径或连接对象；无混合同步时明确标记关闭。
- HybridStore 公开共享同步通道的等待数与容量、日志同步操作状态、日志任务累计失败/丢弃，以及请求历史原有独立同步预算。日志共享队列包含两种任务；请求历史 `queued` 延续包含正在执行批次的语义。
- `syncToSQLite` 和成功结算的副本同步都记录实际结果。任何同步失败后置 `cache_may_be_stale=true`；后续无关写入成功不清除它，因为无法证明旧差异已修复。UI 提示“副本需核对”，同时展示最近同步成功时间。
- SyncManager 记录配置恢复、可选日志恢复、可选请求历史恢复的结果。工厂把完整启动结果交给 HybridStore。可选历史恢复失败仍按原逻辑允许启动，但面板显示历史可能不完整；`logDays=0` 明确未启用历史恢复。
- 未提供启动结果的手工 HybridStore 显示未知，不能凭构造成功宣称恢复完成。
- 关闭时丢弃日志同步任务也计入累计损失。指标不能提供丢弃记录的自动补发功能。

## API 结构与状态规则

原有 `responses_websocket`、`billing`、`token_failure_stats`、`request_traces` 保留。新增：

- `started_at`、`observed_at`：Server 起始时间、此次快照时间。
- `logs`：启用、通道/批次等待、记录写入/丢弃/最终失败、操作状态。
- `cleanup.logs`、`cleanup.debug_logs`：是否启用、保留时间、周期、下一次计划时间、实际操作状态；调试日志还公开已删除条数和清理模式。
- `storage`：存储类别、副本状态、日志同步和启动恢复；不公开错误文本。
- `health`：`version=1`、总体 `state` 与固定组件 ID 对应的 `state`、`reason`。状态/原因均为受控枚举，前端负责中文文案。

组件：`billing`、`request_history`、`logs`、`token_stats`、`log_replication`、`trace_replication`、`cache_sync`、`log_cleanup`、`debug_cleanup`、`startup_recovery`、`websocket`。

| 状态 | 含义 |
| --- | --- |
| `blocked` | journal 不可用或正在关停，已暂停新的代理准入 |
| `error` | 当前结算或写入操作失败，或仍有内存结算事件 |
| `warning` | 队列压力、近期丢弃、持久积压、清理/历史恢复失败，或副本差异待核对 |
| `working` | 有积压或操作正在执行，尚无更高优先级问题 |
| `healthy` | 已观测到对应成功，当前无已知问题 |
| `idle` | 功能已启用，但尚无对应操作，或当前无会话 |
| `disabled` | 当前部署/配置未启用这项功能，不作为故障 |
| `unknown` | 缺少必要状态依据，不显示健康 |

总体优先级：blocked > error > warning > unknown > working > healthy > idle；disabled 不参与故障判断。WebSocket 只按当前资源压力判断，重连、心跳失败与拒绝的累计数不自动变成当前故障。

## 页面与交互

新增管理员控制台 `#/health`，导航名称“运行健康”，加入全局搜索。沿用当前字体、绿/琥珀/珊瑚色状态令牌和精细边框，用紧凑状态行与数字区分层次，不重做其他页面。

```text
运行健康                         每 10 秒自动刷新  刷新  复制脱敏诊断
当前状态 · 是否暂停准入          快照时间 / 进程启动时间

费用与请求记录
  可靠结算                      请求历史写入
  当前积压/在内存/最后确认        通道等待/批次待写/未保存记录

写入与同步
  上游日志 / 失败请求统计 / 日志同步 / 请求历史同步 / 副本核对

维护与恢复
  日志保留清理 / 调试日志清理 / 启动恢复

WebSocket 资源
  下游连接 / 上游连接 / 执行会话 / transcript 预算 / 累计拒绝
```

- 首页显示独立健康摘要，业务概览加载失败时仍可读。首页范围切换不重置运行指标。
- 详情页每次完成后安排下一次刷新，默认间隔 10 秒；请求超时 8 秒，同一页不重叠请求。隐藏页面暂停轮询，回来立即更新；可手动暂停与刷新。
- 刷新失败保留上次快照，明确标记“当前状态未知”；最后成功接收超过 30 秒标记过期。暂停时说明显示的是上次快照。
- 后端缺少新版 `health` 或返回 404 时显示版本/接口不可用，不能把缺字段补成全绿的 0。
- 复制诊断显式投影允许的计数、时间、状态和模式；额外字段、错误原文、路径、凭据或 DSN 均不进入诊断。过期诊断注明快照状态。
- 可展开最近处理与累计记录；告警、损失和处理建议不藏在纯图标里。使用现有日志/设置入口，不提供未经实现的重试、补发或修复按钮。
- 320px、390px、1440px，深浅主题、键盘焦点、reduced-motion 均验证。

## 验收

1. 可复现失败、重试成功、取消、无操作、关闭功能和未提供数据；计数与时间含义符合真实路径。
2. journal 故障仍 503；面板能读，无数据库探测副作用。
3. 普通及调试清理失败可见，成功后显示恢复时间，累计失败保留；关闭/未运行不冒充成功。
4. 本地请求历史写入与主库复制分开；后续成功不暗示损失自动恢复。
5. 副本同步失败后无关成功不能消除待核对状态；启动历史部分失败不被最终“启动成功”掩盖。
6. 旧接口和未授权会话不泄漏指标；脱敏诊断不包含合成秘密。
7. 后端相关回归、全量内部测试、lint、构建与前端测试、类型检查、构建、合成浏览器检查通过。
8. 差异整合前后核对源码及保护文件哈希，清除本阶段拥有的工作区、依赖链接与验证程序，保留紧凑证据。
