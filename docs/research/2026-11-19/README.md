## 主要结论

以下结论、最初缺口和版本表保留为 2026-11-19 的研究快照；当前本地实施状态以上方阶段结果为准。

PivotFlow 当前已经是具有站点控制面的个人 AI 网关：路由、四协议转换、多 Key / 多 URL、Responses WebSocket、价格与费用、签到、通知、备份和 React 控制台均已实现主要路径。下一阶段最有价值的方向是让现有能力形成连续任务：**接入顺畅，调用可靠，失败可解释，费用与恢复可信**。

源码与远端 main 同为 v0.4.9 对应的 `90aee95`；本机保留的 `pivotflow.exe` 却来自 v0.4.8 的 `6bc0ebe`。此外，计费队列持续满时仍可能漏记成功统计、活动请求没有持久尝试历史、健康指标不覆盖主要后台队列、带认证请求的重定向规则不完整，都是应优先处理的具体边界。

参考项目提供了不同方向的经验，不能把它们的功能数量直接相加。ccLoad 更适合学习数据面和客户端接入；Octopus 更适合学习能力配置及请求证据；All API Hub 更适合学习账号工作流、任务恢复和浏览器辅助。

## 三个项目近期最值得学习的变化

**ccLoad**：5.0 增加和修正更多 OAuth 提供商、订阅额度窗口、隐私遮罩、动态 reasoning、Responses 压缩与流终止边界；后续 beta 修复 Codex refresh history、模型选择器、跨协议 tool schema 和 Anthropic 旧配额窗口。对 PivotFlow 最有价值的是对认证转发、会话/线程亲和、物理连接资源、费用超额窗口和客户端配置的精细处理。已有的连接代际轮换、分类冷却和 WS 生命周期应继续沿用。

**Octopus**：最近主线重构到多 Key 与“模型 × Key × 协议”授权矩阵，强化实际渠道 Key、token speed、缓存率、实时状态、取消与严格流终止检查；v0.13.13 本身是依赖升级。分步编辑、三级候选、运行态倒计时和逐轮日志很值得借鉴。当前上游只有 manual / failover，且不含 Gemini / Images / WS；不能根据旧截图或 fork 推断它仍有轮询、随机、加权。

**All API Hub**：4.9 的按站点请求预算与 429 冷却、按账号组独立比较报价，4.10 的 Cookie / 登录恢复、API 与 CLI 验证工作区、可续跑上下文探测、费用单位与大模型目录修正，以及 Nightly 的按账号/日期确认签到结果、响应式流式测试和反馈精简，对便利性与可靠性都有直接参考价值。它是浏览器内的资产管理与网关控制工具，扩展权限和已登录会话不能自然搬到服务端网关。

## 建议的实施顺序

1. **可信运行**：成功计费的饱和与恢复路径、认证重定向规则、流式和 WS 不重放边界；随后将请求身份、尝试历史和后台队列健康连接起来。
2. **连续接入和维护**：来源 → 模型/能力验证 → 渠道差异预览 → 下游令牌 → 客户端配置 → 首次请求；站点任务共享预算、错误分类、只重试失败，备份可在独立数据库验证恢复。
3. **在证据充分后扩展**：显式会话亲和、只读能力矩阵、周期 Token 限额、OAuth 配额窗口、受限自助查询和浏览器辅助。UI 先改善默认信息层次、操作可达和规模体验。

整体排序见 [建议与验收](recommendations.md)。各子报告的优先级是单项目研究视角，不应直接合并为一个大型开发任务。

## 实际验证与边界

- 前端 TypeScript 检查通过，现有 167 项测试通过。它们验证现有逻辑与源码守卫，不等于真实浏览器或所有客户端验收。
- 后端 33 个有测试的内部包最终通过，另有 5 个包无测试文件。首次直连因依赖下载超时失败；临时镜像完整测试有 32 包通过，应用包触及缩短后的 120 秒总时限，单独以 Go 默认十分钟上限补跑后在 80.17 秒通过。初次失败和补跑日志均保留，见 [验证记录](pivotflow-current-state.md)。临时缓存已清除，未修改系统 Go / 代理配置。
- 清理以原始追踪文件和保护文件的 SHA-256 为基线。归档内容先通过 CRC / 逐文件哈希校验，再删除临时副本；最终结果见清理记录。
- 未启动生产服务、使用真实上游账号或进行真实签到，也没有提交、推送或发布。竞品 UI 的截图观察、源码推断和未实测事项在子报告中分别标明。

ccLoad 为 MIT；Octopus 与 All API Hub 为 AGPL-3.0。研究和独立实现交互思想可以推进；实际复用源码时应保留来源、核对具体子目录许可证，并明确其与 PivotFlow MIT 发行方式的关系。
