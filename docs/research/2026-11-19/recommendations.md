## 1. 建议的产品方向

目标是让用户从“有一组上游账号或 Key”顺畅走到“客户端能稳定调用，失败时知道原因，费用和数据可信”。保留已有站点控制面，将接入、路由、观测和恢复连接起来。

| 可选方向 | 优点 | 代价 | 建议 |
| --- | --- | --- | --- |
| 继续以站点资产门户为主 | 余额、签到、价格和公告操作方便，功能容易展示 | 路由正确性与故障排查的改进容易被挤到后面 | 保留这部分能力，让它服务于接入与维护 |
| 个人 AI 网关为主，站点管理作为控制面 | 与现有数据面优势和用户目标一致，能围绕完整任务优化 | 需要把日志、费用、重试、配置生效等细节做扎实 | **推荐作为下一阶段主线** |
| 多租户商业平台 | 可拓展组织、成员、计费和运营 | RBAC、隔离、账本、支付、组织配额和运维复杂度明显增加 | 当前先保持个人部署边界；确有多用户需求再单独设计 |

参考项目各有适合学习的部分：ccLoad 的数据面演进、Octopus 的路由产品与操作组织、All API Hub 的账号管理与浏览器工作流。学习的单位应是“解决了哪个具体问题”，而不是把三套功能与 UI 全部合并。

### 3.1 先完成计费与恢复正确性

代码已修复数据库统计更新失败时的限额开放路径，但队列饱和 100ms 后仍可能丢弃成功统计。建议把“请求费用结算”与“用于 UI 的可丢弃统计”分开：成功费用需要可重试的结算记录和幂等身份；普通失败统计仍可在饱和时降级。不要简单把队列无限增大，也不要在响应路径加没有截止时间的阻塞。

同时写清楚目前的成本限额是软限额：用量在完成后才知道，已经准入的并发请求可能超过阈值。个人部署先通过并发限制收敛暴露；只有确实需要严格额度时，才引入预留、结算、退款。不能把软限制换一个标签就称为严格预算。

故障测试使用现有 mock 上游：401、403、429 与 reset、5xx、DNS/连接错误、首字超时、半截 SSE、客户端取消、重复工具输出、未知 previous_response_id、WS 容量与 transcript 拒绝。重点核验可观察行为和费用，不能仅检查某个内部分支被调用。

### 3.2 把日志变成一次请求的解释

当前活动请求已有进程内 ID，并在多个尝试间复用，但它只保留当前快照、完成即删除，日志也未保存。行 ID 和该运行期 ID 还不能形成可持久查询的完整请求身份。应复用已有 BeginAttempt 生命周期，把准入、等待、候选选择、协议协商、上游尝试和最终响应关联起来；每次尝试另有序号。客户端可带合法且有限长度的关联信息，否则由网关生成。

在 UI 里，用户应看到的是下面这样的任务记录，而不是翻多行日志猜测：

```text
请求 pf_req_…  · 最终成功 · 模型别名 → 实际模型 · 客户端协议 → 上游协议
  01  渠道 A / Key #2 / URL 1   429，按上游 reset 冷却
  02  渠道 B / Key #1 / URL 1   首字超时，尝试同渠道备用 URL
  03  渠道 B / Key #1 / URL 2   成功，首字 / 总耗时 / 用量 / 费用来源

相关操作：查看只读路由诊断 · 查看 Key 状态 · 仅检测该端点 · 复制脱敏诊断
```

这份时间线必须按真实执行记录生成。候选诊断是某一时刻的只读解释，不能当作过去实际尝试的替代，也不能靠调用诊断推进轮询来“预测下一次”。

例如一个客户端请求先在 A 返回 429，再经 B 成功：客户端最终成功数应为 1，上游尝试数应为 2。两种成功率、限流次数、客户端取消、部分输出后失败与探测流量分开显示，避免把正常故障切换解释成客户端调用失败，也避免隐藏上游质量问题。

### 3.3 把站点维护做成可解释的任务

站点余额、账号凭证、签到能力、模型 Key 和渠道状态是不同事实。建议统一显示“当前状态、最后成功、最后尝试、原因、下一步”，避免一个绿色余额掩盖没有模型调用 Key，或把 WAF 拦截解释成账号过期。

按站点共享并发和频率预算；余额、公告、模型和价目表的重复请求合并；定时任务随机错峰；失败分类决定重试和人工操作。状态至少包括等待、运行、成功、部分成功、可重试失败、需重新认证、需浏览器操作、已取消。

All API Hub 在用户浏览器内可以访问扩展权限和已登录会话。服务端 PivotFlow 无法自然获得这些能力，不能直接搬浏览器请求代码，也不能通过反复请求“解决”人机验证。浏览器辅助应是独立、受限、由用户发起的导入或验证流程。

### 3.4 接入引导不要求用户先理解全部配置

建议利用已有能力串起五步，不重新发明站点/账号/渠道：

1. **添加来源**：站点账号、API Key 或 OAuth；按 Provider 显示必要凭证，给出访问地址与代理检查。
2. **发现并验证**：识别平台、列出模型/Key、说明可管理能力；失败明确缺哪项，保留已填内容。
3. **预览渠道**：展示来源绑定、用户组、URL、协议、模型、Key；确认后幂等同步。
4. **生成客户端配置**：选择 Claude Code、Codex、Gemini 或 OpenAI SDK；展示 endpoint、访问令牌权限和精确配置模板。
5. **发出首个测试**：沿真实代理入口验证；成功后链接到请求记录，失败时进入同一请求的尝试解释。

“复制配置”只是客户端配置的起点。配置生成器需要按客户端版本维护测试样本，不应猜配置字段。涉及客户端文件写入的工具以后单独设计；本次建议首先提供可复制、可下载的内容，避免覆盖用户已有设置。

## 4. UI 学习应落实到任务，而不仅是配色

### 4.1 默认导航保持现有概念

保留站点、账号、渠道和访问令牌的角色，减少同一信息在多个页面换名字。建议按任务组织导航而不再增加重复统计页：

```text
使用与接入        维护上游          观察与排障        系统
概览              站点 / 账号       请求日志          设置
客户端接入        签到 / 公告       数据面板          备份与导入
渠道与模型        OAuth / 凭证      健康与诊断        系统访问
访问令牌
```

这是信息组织建议，不是本轮改过的导航。最终名称应与用户正在使用的控制台保持连续，避免不必要的重命名。

### 4.2 首页回答三个问题

- **现在能用吗**：可用模型/渠道、正在影响调用的错误、需要处理的凭证或余额问题。
- **最近发生了什么**：调用量、成功率、首字耗时、费用及数据更新时间；失败状态可点开对应日志。
- **接下来做什么**：新增来源、同步模型、配置客户端、只重试失败任务、恢复备份。

已有数据面板能展示趋势与分配。首页不必再复制一个完整统计页，应该把“需要处理”的入口和数据来源放到最容易发现的位置。

### 4.3 列表采用一致的信息层次

| 行内元素 | 应表达的意义 |
| --- | --- |
| 名称与来源 | 当前对象及它来自哪个站点/账号/导入 |
| 状态与原因 | 可用、冷却、停用、缺 Key、待同步等，颜色之外必须有文字 |
| 主操作 | 用户此刻最可能需要的动作，如检测、恢复凭证、重试失败 |
| 数字 | 金额、耗时、比例和更新时刻；同一列统一精度，不把未知显示为 0 |
| 更多操作 | 低频编辑、导出、删除等；给批量行为一致的预览与逐项结果 |

长名称、URL 和模型名需要在窄屏可读；更多菜单、Tooltip 和搜索弹层不能被页头、卡片 overflow 或 backdrop-filter 的包含块裁剪。现有 AnchoredPopover、Portal 和样式修正应作为统一组件继续复用。

### 4.4 视觉与性能的取舍

PivotFlow 已投入很多主题、玻璃、壁纸与文字自适应工作。继续保持默认对比度和信息密度；装饰应可关闭，滚动性能以现有真实浏览器预算回归。移动端、关闭硬件加速、弱设备、超长列表和 reduced-motion 是有代表性的验证条件。

对参考 UI 的学习要标记证据类型：公开截图说明布局和视觉，源码说明交互与断点，运行 demo 才说明实际行为。不要把一张桌面截图当成移动端或键盘体验证明。三个项目的具体视觉与实现证据分别在 [ccLoad](ccload.md)、[Octopus](octopus.md)、[All API Hub](all-api-hub.md)、[PivotFlow 自身 UI](pivotflow-ui-audit.md) 中。

## 5. 容易走错的几个方向

| 方向 | 为什么需要克制 | 合适的替代 |
| --- | --- | --- |
| 全量覆盖 ccLoad / 转换核心源码 | PivotFlow 有控制面、来源绑定、计费口径、固定会话身份和本地协议契约 | 固定提交、逐项移植、按现有同步 Skill 做双层回归 |
| 把浏览器自动化直接放到网关核心 | Cookie、扩展权限和人机验证属于浏览器环境，可靠性与服务端生命周期不同 | 有界的辅助导入/验证流程，与代理数据面隔离 |
| 先加复杂的“最低价智能路由” | 站点组倍率、缓存、按次价格、不可评估表达式和真实可用性都会影响成本 | 先解释价格来源与候选状态；可靠价格下才开放显式策略 |
| 把各种缓存混为一谈 | 上游 prompt cache、网关响应缓存、配置快照、连接与会话复用语义不同 | 各自的指标与开关；先改善已有复用和计费说明 |
| 只靠增大队列、重试次数或超时提高可靠性 | 可能增加内存、费用与 WAF 压力，并推迟显性失败 | 有截止时间的降级、幂等结算、按站点预算、明确恢复边界 |
| 同时重做所有页面和后端 | 变化面过大，难区分新体验与行为退化 | 按完整用户任务交付，一项一项用现有源码与浏览器验证 |
| 把“站点价目计算”写成“上游账单确认” | 当前是由价格与用量推导，复杂规则或上游扣费仍可有差异 | 显示来源、时刻和估算；实际对账另行记录 |

## 6. 持续学习机制

每次参考项目更新保留一条记录：仓库、版本 / SHA、发布日期、涉及模块、用户问题、PivotFlow 已有程度、是否值得移植、许可证、适配风险、验证结果和决定。来源用不可变提交链接；main 中的实现和 Release / 浏览器商店的发布分开。

建议每月集中审阅一次，协议或关键故障修复另设短周期。不要为每个上游发布都立刻重新设计产品；先用功能差距矩阵判断它解决的问题是否真实存在。保留源码与对应测试来源，写明采用、暂缓或不适用，避免后续代理重复提出已经完成或被否决的方案。

## 7. 建议的三个里程碑

- **A：可信的运行与费用**。完成 P0、请求关联、核心降级指标与价格语义，已有协议和故障行为保持稳定。
- **B：方便的接入与维护**。完成接入引导、客户端配置、任务预算、同步差异和恢复验证；UI 调整围绕这条完整路径。
- **C：有证据的策略与集成**。在 A、B 稳定后，再评估模型分组策略、浏览器辅助与可选缓存，不把探索性功能默认打开。

没有给出未经估算的开发天数或虚构性能数字。实施前应从这些里程碑中选择一个可独立验收的任务，读取对应源码和现有测试，写清具体设计与回滚方式。
